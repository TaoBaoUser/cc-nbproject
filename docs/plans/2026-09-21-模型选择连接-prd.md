## 1. 背景：这条链路的由来

设计文档 6.6 最初把选模型做成了一条「填表流水线」：在编辑框里拉列表 → 选源模型名 →
选目标模型 → 点「添加」写进文本框 → 保存。6.7 推翻了它，理由记在那里，本文只重复结论：

- **换了模型不该比换供应商更麻烦。** 加供应商是配一次就不动的事，换模型是想换就换的事。
  捆在一起的代价是：每换一次模型都要开编辑框走一遍流水线。
- **源模型名不该由用户选。** Claude Code 会发什么名字是 `~/.claude/settings.json` 里
  已经定好的**事实**，不是偏好。工具自己读出来即可，让用户挑等于把能自动完成的事伪装成选项。

于是模型选择移到卡片上，两个字段的标签直接写「主模型」「后台小任务」，
**底层写的是同一份 `modelMap`**，`proxy.js` 一行未改（见 6.7「一个关键的实现选择」）。

### 一条贯穿全文的红线

`/v1/models` **不属于 Anthropic 兼容规范**，覆盖面无任何保证 —— 实测 OpenRouter 有
（200，446 个模型），DeepSeek 没有（404）。因此：

> 拉取只能当**辅助**，手工输入必须**始终**可用。
> 任何让「拉不到列表就当机」的改动都是回归，不是优化。

这条同时约束 UI 与验收：**候选为空时输入框必须退化为普通文本框**，不是禁用态。

## 2. 需求条目

### R1 —— 候选按需拉取，不预热、不重复拉

| 项       | 内容                                                                                            |
| -------- | ----------------------------------------------------------------------------------------------- |
| 需求     | 聚焦模型输入框时才拉 `/v1/models`；同一份列表在一次会话内不重复下载                             |
| 现状     | [ModelPicker.tsx:85](../../src/renderer/components/ModelPicker.tsx#L85) 首次聚焦触发；主进程按 `baseUrl + key 尾 8 位` 缓存 10 分钟（[models.js:182](../../src/main/models.js#L182)） |
| 验收标准 | 首次聚焦到出候选的耗时不超过端点真实往返 + 渲染；再次聚焦不打上游（缓存命中）                    |
| 验证方式 | 冒烟第 6b 步（聚焦后 1.5s 内候选就绪，依赖缓存）                                                 |

**为什么按需而不是页面加载就拉**：OpenRouter 那份有 738KB，窗口里可能挂着七八个供应商，
全量预热等于开一次窗口下几 MB。**为什么在 `ModelPicker` 而不是每个字段各自持有一份**：
候选是「这个供应商有什么模型」，与字段无关。

### R2 —— 拉取失败要翻译成能照着做的话，而不是报错

六种失败各自指向完全不同的下一步，这是 `models.js` 里 `kind` 存在的原因，UI 侧不能把它们
揉成一句「拉取失败」：

| `kind`          | 用户该做什么            | 界面文案                                            |
| --------------- | ----------------------- | --------------------------------------------------- |
| `unsupported`   | 手打模型 ID（**不是错误**） | 「该供应商没有 /v1/models 接口，可直接手打模型 ID」 |
| `auth_failed`   | 去改 key                | 「认证失败 —— 请检查 API key，可直接手打模型 ID」    |
| `network_error` | 检查网络 / 代理          | 「无法连接 —— <原因>，可直接手打模型 ID」            |
| `invalid_url`   | 去改地址                | 「Base URL 不是合法 URL，可直接手打模型 ID」         |
| `empty`         | 手打                    | 「接口有响应但没有返回任何模型，可直接手打模型 ID」  |
| `upstream_error`| 看上游原话              | 上游原始报错摘要 + 「可直接手打模型 ID」             |

| 项       | 内容                                                                     |
| -------- | ------------------------------------------------------------------------ |
| 现状     | [describe.ts:38](../../src/renderer/describe.ts#L38) 负责翻译，`ModelPicker` 统一追加「可直接手打模型 ID」 |
| 验收标准 | 六种 kind 都能落到具体文案；失败后状态栏**不得**停在「正在拉取模型列表…」 |
| 验证方式 | 单测覆盖分类（`test/models.test.js`）；**文案本身目前无自动化守护**，需冒烟或手工 |

**「不卡在正在拉取」靠什么**：主进程 20s 超时（`DEFAULT_TIMEOUT_MS`），超时后归为
`network_error`，文案里带上「请求超时（20000ms）」。所以它不会永久卡住，但**最长会静默 20 秒**。

### R3 —— 手工输入永远是可用路径（红线）

| 项       | 内容                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------- |
| 需求     | 无论拉取成功、失败、还是压根没调，输入框都要能自由输入任意模型 ID 并保存                           |
| 现状     | `Combobox` 是 `<input>` + 候选列表，不是 `<select>`；候选为空时不渲染浮层，输入框退化为普通文本框（[Combobox.tsx:118](../../src/renderer/components/Combobox.tsx#L118)） |
| 验收标准 | 供应商没有 `/v1/models`（DeepSeek 场景）时，手打任意 ID 仍能落盘                                    |
| 验证方式 | 冒烟第 7 步走的是自由文本路径；DeepSeek 场景需手工验一次                                            |

### R4 —— 拉取成功后全量进候选，并对空字段给出可一键采纳的建议

| 项       | 内容                                                                                          |
| -------- | --------------------------------------------------------------------------------------------- |
| 需求     | 全部模型 ID 进候选，无遗漏；对**空**字段用 `suggestModelMapping()` 猜一个目标名，做成 chip      |
| 现状     | 候选 = `result.models` 全量（无截断、无分组）；建议只对 `map[field.name]` 为空的字段生成（[ModelPicker.tsx:103](../../src/renderer/components/ModelPicker.tsx#L103)） |
| 验收标准 | 「可选 N 个模型」的 N 与供应商实际返回条数一致；chip 点一下即采纳并落盘                          |
| 验证方式 | 冒烟第 4 步（候选数）+ 第 5 步（采纳落盘）                                                      |

> **刻意不自动写入映射。** 猜测只在用户点 chip 时落盘 —— 悄悄改掉用户正在用的模型，
> 后果是账单和输出质量同时变化，而用户不知道为什么。这一条是需求，不是实现细节。

**推论（验收时注意）**：字段已经有值时**不会**出现 chip。所以「拉取后没看到建议」既可能是
猜不中，也可能是字段已被填过。清单第 2 节的「猜对源模型名时出现建议 chip」隐含前提是
**该字段为空**，验收时先把字段清空再判断。

### R5 —— 改完立即保存，没有「保存」按钮；清空即取消映射

| 项       | 内容                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------ |
| 需求     | 选中 / 输入 / 清空都立即落盘；清空 = 删掉这条规则（原样透传），**不能**留一条空规则                      |
| 现状     | `commit()` 落盘（[ModelPicker.tsx:76](../../src/renderer/components/ModelPicker.tsx#L76)）；值为空则 `delete next[name]`；状态栏回「已改回原样透传」 |
| 验收标准 | 任何一次改动后立刻 `listProfiles()` 就能看到；清空后 `modelMap` 里不留该键                               |
| 验证方式 | 冒烟第 5 / 6b / 7 步                                                                                    |

**为什么不能留空规则**：一条空规则会让请求带着空模型名出去，上游回一个完全不指向原因的 400。

### R6 —— 卡片标签用 Claude Code 的真实模型名，源名要能看到

| 项       | 内容                                                                                          |
| -------- | --------------------------------------------------------------------------------------------- |
| 需求     | 两行分别标「主模型」「后台小任务」；源模型名（映射左列）以 `title` 露出，便于核对              |
| 现状     | 标签是字面量，`title={field.name}`（[ModelPicker.tsx:119](../../src/renderer/components/ModelPicker.tsx#L119)）；归类由 `classifyModelNames()` 按配置键判定，不按名字猜 |
| 验收标准 | 标签与字段对应关系正确；同一模型名同时占两类时只留「主模型」一行；只有一种模型名时只有一行     |
| 验证方式 | 单测覆盖归类（`test/setup.test.js` 的 `classifyModelNames` 六个用例）；界面表现由冒烟第 1 步断言标签存在 |

### R7 —— 下拉可滚动、可键盘操作、可边打边筛

| 项       | 内容                                                                                            |
| -------- | ----------------------------------------------------------------------------------------------- |
| 需求     | 候选浮层可上下滚动；↑↓ 高亮、Enter 选中、Esc 收起；输入即筛；446 个候选也能定位                  |
| 现状     | 自写 `Combobox` 取代原生 `<datalist>`（后者的浮层由浏览器渲染，样式与滚动都不可控，正是清单第 4 节的原始痛点）；`.combobox-list` 为 `max-height: 240px` + `overflow-y: auto` |
| 验收标准 | `scrollHeight > clientHeight` 成立；输入 `flash` 后候选收窄且**全部**命中；键盘选中立即落盘、列表收起 |
| 验证方式 | 冒烟第 4 步（可滚动）、6b 步（筛选 + 键盘选中落盘）                                             |

### R8 —— 不碰数据模型，不干扰卡片自身行为

| 项       | 内容                                                                                       |
| -------- | ------------------------------------------------------------------------------------------ |
| 需求     | 两个下拉写的是同一份 `modelMap`；`proxy.js` 零改动；在模型框里点击**不得**触发卡片切换供应商 |
| 现状     | `map` 直通 `updateProfile({ modelMap })`；模型区整体 `stopPropagation()`（[ModelPicker.tsx:115](../../src/renderer/components/ModelPicker.tsx#L115)） |
| 验收标准 | 点模型框前后 `is-active` 状态不变；代理侧行为无变化                                          |
| 验证方式 | 冒烟第 6 步 + `test/proxy.test.js`（回归）                                                  |

**推论：双入口必须互相同步。** 卡片下拉与「编辑 → 高级」文本框是同一份数据的两扇门，
而编辑框是**用 `profile.modelMap` 预填、保存时整体覆盖**的。所以卡片落盘后必须让内存里那份
profile 也是新的（[useProfiles.ts:82](../../src/renderer/hooks/useProfiles.ts#L82) 用返回值
替换列表元素即为此），否则会出现「卡片上选好模型 → 打开编辑框看到空的 → 点保存 → 刚选的没了」。
这条是设计文档 6.7 记录的丢数据路径，冒烟 5b 步专门守它。

## 3. 缺口（批准后要执行的工作项）

以下是**读代码发现的、清单里没有的问题**。按影响排序。

### W1 ★ 拉取失败之后，没有任何重试路径

**现象**：`ModelPicker` 用一个 `fetchStarted` 布尔量挡住重复拉取，但它在**发起**时就置位，
而不是在成功时：

```js
if (fetchStarted) return;     // ModelPicker.tsx:86
setFetchStarted(true);        // ModelPicker.tsx:87  ← 失败后也永远为 true
```

于是这条路径被彻底堵死：

```
聚焦 → key 是错的 → 「认证失败 —— 请检查 API key，可直接手打模型 ID」
  → 打开编辑框把 key 改对 → 回到卡片再聚焦 → 仍然一句「认证失败」，候选永远为空
```

组件不会重挂载（[ProvidersView.tsx:26](../../src/renderer/views/ProvidersView.tsx#L26) 的
`key={p.id}` 不变），三个视图也是常驻挂载只切 CSS class（[App.tsx:41-51](../../src/renderer/App.tsx#L41-L51)），
所以切页签也救不回来 —— 只能重启应用。

**这不是小疏忽，是和既有设计意图直接冲突。** 主进程特意做了两件事来支持「改完 key 重试」：

- 失败结果**不进缓存**（[models.js:197](../../src/main/models.js#L197)）
- 缓存键带上 key 尾 8 位，换 key 即换缓存（[models.js:187](../../src/main/models.js#L187)）

`test/models.test.js` 里甚至有一条测试就叫**「缓存：失败结果不被缓存 —— 改完 key 重试必须真的重试」**。
那条测试是绿的，而它在界面上根本不成立 —— 正是设计文档 9.1 记录的那类
「代码正确、测试全绿，但它跑不到」的故障。

**建议做法**（推荐 a）：

| 方案 | 做法                                                                     | 代价                                                     |
| ---- | ------------------------------------------------------------------------ | -------------------------------------------------------- |
| a ✅  | `fetchStarted` 只记「已成功拿到列表」；失败保持可重拉，成功仍走缓存       | 最小改动，正合主进程的缓存语义                            |
| b    | 在 `baseUrl` / `apiKey` 变化时重置该标志                                  | 能治「改完 key」这一条，但网络抖动失败仍卡死              |
| c    | 每次聚焦都 `force: true`                                                  | 废掉 10 分钟缓存，OpenRouter 每次聚焦重下 738KB —— 不可取 |

**验收标准**：key 填错 → 改对 → 再聚焦 → 能拉到候选。这条必须进冒烟检查（**能被自动化验的 bug 不该只靠手点**）。

> **已修（2026-09-21）**，做法取方案 a：那个布尔量换成 `fetchingRef`（`useRef`），
> 只在请求**进行中**挡住重复拉取，请求一结束（无论成败）就释放 ——
> 「要不要重拉」交给主进程的缓存决定，组件不再自己记一份与它矛盾的状态。
> 冒烟第 8 步钉住：把地址改成 `http://cc-nbproject-smoke.invalid/api`（RFC 2606 保留域，
> 保证解析不了）逼出失败 → 断言文案可照做 → 改回真地址再聚焦 → 断言文案不再是「无法连接」。
> 另有一条前置断言确认地址**真的换掉了**（编辑框保存后卡片显示新地址），否则整个检查会假通过。
> 反向验证：把修复临时改回原样，冒烟如实报出
> 「断言失败：拉取失败时应给出可照做的提示，实际：已改回原样透传」。

### W2 ★ 读不到 Claude Code 模型名之后，同样没有重试路径

**现象**：`ModelPicker` 用模块级 promise 缓存整页只读一次的结果
（[ModelPicker.tsx:11](../../src/renderer/components/ModelPicker.tsx#L11)），而**失败结果也被缓存**：
`ok:false` 一旦拿到，整个进程生命周期内不会再问第二次。

**可达路径不是边角**：`setup.js` 的首次引导**刻意不写** `ANTHROPIC_MODEL`
（[setup.js:76](../../src/main/setup.js#L76)：「那些是用户对自己所用模型的配置」）。
所以在新机器上第一次跑完引导后，若用户原本的 `settings.json` 里没有 `_MODEL` 键，
卡片上两行都不出现，只留一句「读不到 Claude Code 的模型名，请到「编辑 → 高级」手动填写映射」——
**然后永远停在这句话上**，哪怕用户随后自己去填好了模型名。

**建议做法**：给这句警告配一个「重新读取」按钮（复用已有的 `getClaudeModelNames()` IPC），
失败不进模块级缓存。改动量小，但它决定「卡片能不能选模型」这个功能对一部分用户是否根本不存在。

**验收标准**：警告态下点「重新读取」，在 `settings.json` 补上 `_MODEL` 后卡片能长出行来。

> **已修（2026-09-21）**：`ok:false` 不再进模块级缓存（拿到失败就把它清空，下次重新问），
> 警告文案旁加一个下划线链接式的「重新读取」按钮，点一次重跑读取。
> 按钮**只在异常态出现**（`namesChecked && fields.length === 0`），正常状态不占版面。
>
> 验证走了临时 `HOME`（见 §8 第 3 条），真实 `~/.claude/settings.json` 全程只读：
>
> | 阶段 | 实测结果 |
> | ---- | -------- |
> | 假 HOME 里 `settings.json` 无 `_MODEL` 键 | 行数 0；文案「读不到 Claude Code 的模型名，请到「编辑 → 高级」手动填写映射重新读取」；警告色 true；有「重新读取」按钮 |
> | 补上 `ANTHROPIC_MODEL` / `ANTHROPIC_SMALL_FAST_MODEL` 后点按钮 | 行数 2；标签 `["主模型","后台小任务"]`；源名提示 `["deepseek-v4-pro","deepseek-flash"]`；文案清空；警告色 false；按钮消失 |
>
> 冒烟第 9 步只做**条件断言**：处于「读不到」状态时必须有「重新读取」入口。
> 用真窗口跑到那个状态需要一份没有 `_MODEL` 键的 `settings.json`，
> 而检查工具**不许**为此去改用户的 `settings.json` —— 所以那一格靠上面的隔离实例补，不靠冒烟。

### W3 拉取期间没有加载态，最长静默 20 秒

状态栏文案会变成「正在拉取模型列表…」，所以不是完全没反馈；但期间没有可点取消、也没有进度感，
超时阈值 20s 对用户不可见。**低优先**，只在 W1 的重试入口做出来之后才有必要一起考虑。

> **本次不做**，未列入第 7 节 —— W1 的重试入口已经让「等不及就改地址重来」这条路成立，
> 加载态的收益不足以单独开一步。留在这里备查。

### W4 两条未实测的边角（列入验证清单，不预设结论）

| 项                       | 疑问                                                                                                              | 怎么验                                   |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 446 条候选的渲染观感     | 候选是**全量渲染**，没有虚拟滚动。446 个 DOM 节点应无压力，但「边打边筛是否足够跟手」未实测                        | 真窗口 + OpenRouter profile 手工点一次   |
| 浮层与 `.main` 滚动盒     | `.main` 是 `overflow-y: auto`，而 `.combobox-list` 是绝对定位。列表末尾那张卡片的下拉会不会把滚动区撑大、被推到折线下？ | 冒烟里加一条「浮层完整可见」的断言再判断 |

两条都**未验证**，所以在本文里只作为待验项，不当成结论 —— 写进验收清单由执行阶段实测后回填。

#### 实测结论（2026-09-21，真 Electron + CDP 量取）

| 项     | 结论                                                                                                                                |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| W4-1   | **通过**。446 个候选全量渲染 + 输入即筛，未观察到卡顿或掉帧，输入 `flash` 后候选收窄且命中项正确。暂不需要虚拟滚动               |
| W4-2   | **不通过 → 已修**（修复不在批准的五步之内，是另行征得同意后做的，见下）                                                            |

**量法**：窗口内两张卡片时量一次；再用一个纯页面内的占位块（`div`，量完即删，不碰任何配置）
把输入框往下推，再量一次。推多高是**算出来的** —— 让输入框底边离 `.main` 底边正好剩 50px，
这时 244px（240 的 `max-height` + 4 的间距）的浮层朝下必然放不下。

| 情形                                | 浮层 bottom − 视口高 | 露出比例 | 备注                     |
| ----------------------------------- | -------------------- | -------- | ------------------------ |
| 两张卡片，页面未滚动（浮层朝下）    | −152                 | 100%     | 有余量，正常             |
| 输入框被推到离底 50px（浮层仍朝下） | **+194**             | **19%**  | 被推出视野，且撑高滚动区 |

> 超出多少只取决于输入框离视口底多近。同一条缺陷量到过三种值：
> 摆到离底 50px 时是 +194（只露出 19%）、另一种摆法是 +130（露出 46%）、
> 第一次最宽松的那次是 +81（露出 66%）。都不完整可见，性质相同，引用时别把数字当常量。
>
> **一处更正**：「撑大滚动区」当时**量法有污染** —— 量的时候页面上已经插着占位块，
> 滚动区本来就是能滚的，`scrollHeight > clientHeight` 恒成立，等于什么都没说明。
> 复核办法：在同一个占位块不动的前提下，把浮层的 `is-up` 类强行去掉，让它按旧样式朝下渲染，比较三种状态：
>
> | 状态（占位块均在）    | `.main.scrollHeight` |
> | --------------------- | -------------------- |
> | 浮层关着              | 1346                 |
> | 浮层朝上（修复后）    | 1346（不撑）         |
> | 浮层朝下（旧样式）    | **1476**（多 130px） |
>
> 结论不变，数字站得住了：朝下的浮层确实会把滚动区撑高，撑高多少 = 它超出视口多少。

**修法**：`Combobox` 在**打开的那一刻**量一次 —— 下方余量不足 244px 且上方更宽裕时，
给浮层加一个 `is-up` 类，`bottom: calc(100% + 4px)` 代替 `top: ...`（阴影方向一并翻过来）。
不跟滚动走：浮层绝对定位在输入框那一行里，相对输入框的位置不会变，跟着滚动量只会让它来回跳。
只在窗口 `resize` 时重算。

**修复后实测**（隔离环境：本地假上游返回 446 个模型，不碰真实供应商）：

| 情形                     | 朝上展开 | 浮层 top/bottom | 视口高 | 完整可见 |
| ------------------------ | -------- | --------------- | ------ | -------- |
| 正常，页面未滚动         | false    | 336 / 576       | 728    | ✅ 行为未变 |
| 输入框被推到离底 50px    | **true** | 410 / 650       | 728    | ✅ 底部还留 78px |

**冒烟断言（第 8b 步）**，这条断言自己踩过一个坑，值得记下来：
第一版靠 `main.scrollTop = main.scrollHeight` 滚到底来摆位置 —— **摘掉修复重跑，它照样绿**。
原因是滚到底时输入框落在哪取决于卡片下面还有多少内容，跟占位块多高无关，那次卡片停在 573px 处、
根本没贴底，等于什么都没测。改成算位置之后，还加了一条**前置断言**：位置没摆对就直接报错，
不许静默通过。之后的反向验证如实报出
「断言失败：输入框贴到视口底部时浮层也要完整可见，实际底边超出视口 194px」（退出码 1，
一次性供应商照常清理干净）。没有候选的端点（DeepSeek）跳过这一条，理由写在脚本里。

前者是能稳定判定的，后者才是用户真正会遇到的故障。

## 8. 已决定的事项（2026-09-21）

1. **W1 修、W2 的「重新读取」入口也做。** W2 表面上像边角，但它决定了一部分用户
   （引导完成时 `settings.json` 里还没有 `_MODEL` 键的）在卡片上**根本看不到模型选择**，
   而那正是这个功能的全部意义。

2. **冒烟检查指向哪个供应商：本机两个形态都有，不必选择。** `ds-demo`
   （`api.deepseek.com/anthropic`，没有 `/v1/models`）验「接口不存在」分支；
   `openrouter`（`openrouter.ai/api`，446 个模型）验「有接口」分支 ——
   正好是第 5 节清单里天然互斥的那两条。默认的 `npm run smoke` 挑名字含 `openrouter` 的
   那个，DeepSeek 分支另跑一次。

   安全性照旧：检查工具只创建/删除它自己的 `__smoke__` 供应商，收尾逐字段核对
   `ds-demo` 与 `openrouter` 一字未变（设计文档 9.1 记了这条为什么必须是硬约束）。

3. **W2 的完整验证走临时 `HOME`，不碰用户真实文件。** 「读不到模型名 → 补好 → 点重新读取
   能长出行来」这条路径要成立，前提是 `settings.json` 里确实没有 `_MODEL` 键。
   制造这个前提**不允许**去改用户真实的 `~/.claude/settings.json`（那是本工具唯一承诺
   只改一次、且必须先备份+确认的文件）。做法是：用 `HOME=<临时目录>` 起一个隔离实例，
   在那个假 HOME 里放一份没有 `_MODEL` 键的 `settings.json` 和一份种子 `profiles.json`，
   在里面把两条路径都走一遍。用户真实配置全程只读不写。
