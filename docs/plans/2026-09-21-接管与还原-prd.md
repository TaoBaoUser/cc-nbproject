## 0. 这份文档要解决什么

本工具目前对 Claude Code 的接管是**单向**的：能接上，接不上就再也回不来。

一旦用户点了「一键接入」，`~/.claude/settings.json` 的 `ANTHROPIC_BASE_URL` 被改成本机代理
（`http://127.0.0.1:8787`）。而应用一关，代理就停了（[index.js:179-181](../../src/main/index.js#L179-L181)
只做 `proxy.stop()`，**从不还原配置文件**），Claude Code 随即指向一个没人监听的端口，
表现为「Claude Code 突然不能用了」。

更糟的是现在**没有任何还原入口**：与接管相关的 IPC 只有 [`claude:preview`](../../src/main/index.js#L147)
和 [`claude:apply`](../../src/main/index.js#L151)（[ccnb.ts:33-34](../../src/renderer/ccnb.ts#L33-L34)；
同族通道还有 `claude:modelNames`），**没有 revert**。用户唯一的退路是手动编辑
`~/.claude/settings.json`，或找到那个 `settings.json.bak.<时间戳>` 备份去比对。
而 `setup.js` 的文件头注释（[setup.js:6-10](../../src/main/setup.js#L6-L10)）恰恰写着
「一旦改坏，用户会看到 Claude Code 突然无法使用，却完全想不到是这个工具造成的，
排查成本极高」—— 这条自己写下的风险，目前正是裸奔状态。

**本文要把接管变成双向的**：开应用才生效，关应用自动回到原样，随时能断开。

## 1. 背景：诊断中确认的事实

2026-09-21 排查「OpenRouter 接不上」，实测确认：

| 事实 | 怎么确认的 |
|---|---|
| 用户的 `~/.claude/settings.json` **从未被本工具接管过** | `ANTHROPIC_AUTH_TOKEN` 是真实的 DeepSeek key，不是占位符 `cc-nbproject-managed`；`~/.claude/` 下没有任何 `.bak.*` |
| 用户当前的 Claude Code 直连 `https://api.deepseek.com/anthropic` | 直接读该文件 |
| 代理转发链路（含带 `modelMap` 的慢路径）本身是好的 | 本地假上游 + 隔离实例：命中改写 / 未命中透传 / 流式 / 头部全部正确 |

也就是说：**今天之所以还没出事，只是因为用户没点过接入**。一旦点了，关掉应用就会命中
上面那条风险。本文把这个缺口补上。

## 2. 需求条目

### R1 —— 接入是「一次授权、长期记住」的

用户点一次「确认写入」即视为授权本工具长期接管。此后**每次启动**自动接管，不再询问。
授权状态持久化在 `~/.cc-nbproject/profiles.json`，重启应用不丢。

### R2 —— 退出即还原

应用退出时，把 `~/.claude/settings.json` 还原到**本次接管之前**的样子。
**应用关闭后，Claude Code 必须回到用户原来的配置，能正常使用。**

若接入前该文件**原本不存在**，还原后也必须仍然不存在 —— 不得凭空留下一个
`{"env": {}}`（见 3.1 的 `fileExisted`）。

### R3 —— 启动即接管（含失败分支）

若授权状态为「已接管」，应用启动、**代理就绪**后自动写入接管配置，用户不需要每次手动点。

**代理未就绪时不得写入**（见 R7），且必须有明确的界面状态（见 R9 的三态），
不能静默失败。

### R4 —— 随时能一键断开

界面上必须有「断开接入」入口：撤销接管 + 清除授权记忆（下次启动不再自动接管）。
断开必须是**用户可见、可独立完成**的动作，不能藏在编辑框或需要手改文件。

### R5 —— 逐键还原，三种情形分别处理

还原**只针对** `ANTHROPIC_BASE_URL` 与 `ANTHROPIC_AUTH_TOKEN`，其余键（模型名、权限、
hooks……）一律不碰。对每个键按当前值判定：

| 当前值 | 含义 | 动作 |
|---|---|---|
| **等于 `applied[key]`** | 是我们写的，没被动过 | 回滚为 `previous[key]`（`null` 则删除该键） |
| **等于 `previous[key]`** | 已经是目标状态（我们刚还原过，或用户自己改回去了） | **不写、不标记、不产生结果项** |
| **其它** | 用户自己改过 | **保持不动**，并在结果里标记，由界面告知「这一项检测到外部修改，已保留你的改动」 |

> 第二条分支是**幂等**的落点：没有它，第二次还原会把「我们刚写回去的原值」误报成
> 「用户改过」，产生假告警。

### R6 —— 残留可识别、可自愈

应用被强杀（`kill -9`、崩溃、断电）时来不及还原，文件里会残留工具写入的值。两条应对：

1. **自愈**：下次启动的自动接管（R3）会重新写入正确的值，残留天然被覆盖。
2. **识别**：任何一次接管写入**之前**，都要认出「当前值其实就是我们自己写的」
   （`ANTHROPIC_AUTH_TOKEN === 'cc-nbproject-managed'`，或 `ANTHROPIC_BASE_URL` 指向本机代理地址）。
   **这种值绝不能被记进 `previous`** —— 否则还原会把占位符写回给 Claude Code，
   用户真正的凭证被彻底丢掉。识别到残留时：不更新该键的 `previous`，并在界面上告知。

> 这条是审查中发现的**数据破坏路径**：`previous` 若被残渣污染，还原就成了「把死值写回」，
> 而工具还会报告「已还原成功」。

### R7 —— 准入条件（两条，缺一不可）

接入前必须同时满足：

1. **代理确实在监听**，拿得到真实的 `proxy.baseUrl`；
2. **存在已激活的供应商**（`store.getActiveProfile()` 非 null）——否则代理对每个请求空转。

任一不满足即**报错拒绝写入**，并把原因显示给用户（第 2 条文案：
「请先在『供应商』页添加并激活一个供应商」）。

> 现状的隐患：[index.js:148](../../src/main/index.js#L148) / [index.js:152](../../src/main/index.js#L152)
> 写着 `proxy.baseUrl || 'http://127.0.0.1:8787'`。`proxy.start()` 抛错时 `baseUrl` 为 `null`，
> 这个兜底会把一个**必然连不上**的地址写进用户的 Claude Code 配置 ——
> 正好制造出本工具最怕的那种「用户完全想不到是工具干的」故障。
>
> 另外注意：**端口被占不等于代理起不来**。[proxy.js:188-213](../../src/main/proxy.js#L188-L213) 的
> `listenWithFallback` 在 8787 被占时会顺延到 8788…8807。因此写进配置的地址必须
> 取自 `proxy.baseUrl`（实听端口），不能取自 `store.getSettings().port`。详见 3.1。

### R8 —— 单实例，且落败实例不得还原

应用必须单实例运行。两个实例会同时持有接管状态，先退出的那个执行还原，
把仍在运行的另一个实例的接管撤掉，用户表现为「用着用着突然断了」。

硬约束（三条都要满足）：

1. `app.requestSingleInstanceLock()` 的判定放在**模块顶层**，**早于**任何退出钩子的注册，
   也早于 `proxy.start()` 与启动接管；
2. 拿不到锁的实例**直接退出，不执行任何还原**（它读到的接管状态是另一个实例写的，
   它无权撤销）；
3. 拿不到锁时打印一条自述并在 `second-instance` 里聚焦已有窗口。自述文案要提到
   `--remote-debugging-port` —— 否则 `scripts/ui-smoke.js` 那种「另起一个实例来调试」
   的用法会变成「启动后立刻静默退出、调试端口根本没开」。

### R9 —— 接管状态三态可见

侧边栏要能看出当前处于哪一种，不能只有「已接管 / 未接管」两态 ——
「授权了但本次没写进去」必须能显示出来：

| 状态 | 判定依据 | 文案 |
|---|---|---|
| 已接管 | `enabled` 为真 **且** 文件里两个键等于 `applied` | 「Claude Code：已接管」+「关闭本应用时会自动还原」 |
| 已授权但本次未生效 | `enabled` 为真 **但** 文件内容不符（代理没起来 / 写入失败） | 「已授权，本次未接管」+ 失败原因 + 按钮改为「重试接管」 |
| 未接管 | `enabled` 为假 | 「Claude Code：未接管」+ 按钮「配置 Claude Code」 |

**并且必须有刷新路径**：接入 / 断开 / 重试成功后立刻刷新状态。
（[App.tsx](../../src/renderer/App.tsx) 已有现成的 `proxy.refresh`，目前无人调用。）

### R10 —— 还原失败的处置，按场景分开

| 场景 | 处置 |
|---|---|
| **退出路径**（`before-quit`） | 弹框**只给一个动作**「仍然退出」。不可以给「留在应用里」——此时窗口可能已全关，应用不在前台，对话框会被压在别的应用后面，用户不点就永远退不出去；系统注销/关机时更没人能点。失败详情随日志输出，并写入 `takeover.lastRestore`。 |
| **界面路径**（点「断开接入」） | 有窗口，可以二选一：「重试」/「仍然断开」。 |

失败信息必须包含：失败原因、备份文件路径、手动恢复步骤。

### R11 —— settings.json 是接管的唯一真相来源

只有 `applyClaudeSettings` **成功落盘之后**，才允许写入 `takeover{enabled:true, …}`。
apply 抛错时：首次接入直接向用户报错返回，**绝不写 `enabled=true`**。

> 否则会留下「`profiles.json` 说已接管、文件其实还是原样」的半接管状态：
> 界面显示「已接管」（R9 按 `enabled` 判定），退出还原又因为文件当前值不等于 `applied`
> 而跳过 —— 两头都对不上，用户却在界面上看到一切正常。

## 3. 设计

### 3.1 存什么

在 `~/.cc-nbproject/profiles.json` 的 `settings` 下新增 `takeover`：

```jsonc
"settings": {
  "port": 8787,
  "takeover": {
    "enabled": true,
    "applied": {                       // 最近一次实际写入文件的值
      "ANTHROPIC_BASE_URL": "http://127.0.0.1:8788",
      "ANTHROPIC_AUTH_TOKEN": "<本次安装随机生成的 localToken>"
      // ⚠️ 本 PRD 写作时这里是公开常量 'cc-nbproject-managed'，
      //    已被审计的 H6 推翻，见第 9.3 节。照抄旧值会把洞重新打开。
    },
    "previous": {                      // 本次接管之前，文件里的实际值
      "ANTHROPIC_BASE_URL": "https://api.deepseek.com/anthropic",
      "ANTHROPIC_AUTH_TOKEN": "sk-…"
    },
    "fileExisted": true,               // 接入前 settings.json 是否存在
    "backupPath": "/Users/…/.claude/settings.json.bak.2026-09-21T14-07-00-000Z",
    "lastApply":   { "ok": true,  "at": "…", "reason": null },
    "lastRestore": { "ok": true,  "at": "…", "reason": null }
  }
}
```

各字段的语义与刷新时机（**这张表是本 PRD 的核心，实现时逐行对照**）：

| 字段 | 语义 | 首次接入 | 启动自动接管 | 退出还原 |
|---|---|---|---|---|
| `enabled` | 用户是否授权长期接管 | 置 true | 不变 | **不变**（只有「断开」才置 false） |
| `applied` | **最近一次写入的**值 | ✅ 写入 | ✅ **刷新** | 不变 |
| `previous` | **本次接管前**的值 | ✅ 写入 | ✅ **刷新** | 读取（还原目标） |
| `backupPath` | 首次接入那一个备份 | ✅ 记录一次 | ❌ 不建、不改 | 不变 |
| `fileExisted` | 接入前文件是否存在 | ✅ 记录 | 不变 | 读取（决定是否删除文件） |
| `lastApply` / `lastRestore` | 供 R9 的三态与 R10 的交代 | ✅ | ✅ | ✅ |

两条容易写错的细节：

- **`previous[key]` 用 `null` 表示「原本没有这个键」**（还原时删除该键），
  不能用 falsy 判断折叠 —— `""`、`0`、`false` 都是合法取值，
  现有的 [`setup.js:99`](../../src/main/setup.js#L99) 那句 `(content.env && content.env[key]) || null`
  会把它们一律记成 `null`。要用 `Object.prototype.hasOwnProperty`。
- **`applied.ANTHROPIC_BASE_URL` 必须取本次的 `proxy.baseUrl`**（实听端口），
  不能取 `store.getSettings().port`。端口漂移时两者不同，写错了会让 R5 的
  「等于 `applied`」判定失配 —— 那是本工具自己写的值被判成「用户手改」，
  结果是**配置永久卡在一个死端口上**。

> 关于把真实 token 存进 `profiles.json`：该文件里已经明文存着所有供应商的 API key
> （[store.js:31-35](../../src/main/store.js#L31-L35)，权限 `0600`），多存一份「接管前的 token」
> 不增加新的暴露面。换来的是**还原不依赖备份文件**——备份可能被用户删掉。

### 3.2 备份只在「首次接管」时产生一次

**这是必须处理的坑**：现在的 `applyClaudeSettings` 每次调用都 `copyFileSync` 出一个
`settings.json.bak.<时间戳>`（[setup.js:130-133](../../src/main/setup.js#L130-L133)）。
若启动自动接管也走这条路，用户一天开十次应用就会在 `~/.claude/` 里堆十个备份文件。

附带的既有缺陷：`previewClaudeSettings` 在预览阶段就调了一次 `makeBackupPath()`
（[setup.js:110](../../src/main/setup.js#L110)）给界面展示，`applyClaudeSettings` 写入时**又调一次**
生成另一个时间戳 —— [SetupModal.tsx:107](../../src/renderer/modals/SetupModal.tsx#L107) 展示给用户的
「写入前会自动备份为：…」和实际产生的文件**不是同一个**。

修法：预览**不再预测备份路径**，只返回布尔语义（`willBackup: exists && 本次是首次接管`），
界面照它显示「写入前会自动备份」或「本次不新建备份（沿用首次接管时的备份）」；
具体路径只由 apply 的返回值给出。

### 3.3 状态机

```
                   用户点「确认写入」（须过 R7 准入）
    未接管 ─────────────────────────────────────▶ 已接管
      ▲                                              │  │
      │  用户点「断开接入」                              │  │ 启动（R3）
      └────────────────────────────────────────────┘  │  写 applied / 刷 previous
                                                       │
      退出（R2 / R5）◀────────────────────────────────┘
      还原为 previous，enabled 保持 true
```

要点：

- **退出不改变授权记忆**。退出只是把文件还原，`enabled` 仍是 `true`，
  这样下次启动才会自动接管。用户想彻底不玩了，才点「断开接入」。
- **断开 = 还原 + `enabled ⇐ false`**，且**只在还原成功之后**才清除 `takeover`；
  还原失败则保留 `previous` 与 `backupPath`，让用户还能再试一次（R10 的界面分支）。
- **断开与「确认写入」必须互斥**：两者都是「读文件 → 算 → 写文件 → 写状态」的复合动作，
  交错执行会写出不一致的状态。用一个模块级的 `busy` 标志挡住重入，第二次调用直接报错返回。
- **代理未就绪是一个合法状态**，不是异常：`enabled` 为真但本轮写不进去时，
  进入 R9 的第二态，界面给「重试接管」。

### 3.4 文件路径必须可注入（重构项）

现在 [setup.js:19-20](../../src/main/setup.js#L19-L20) 把路径写死在模块顶层：

```js
const CLAUDE_DIR = path.join(os.homedir(), '.claude');
const CLAUDE_SETTINGS = path.join(CLAUDE_DIR, 'settings.json');
```

后果是 `test/setup.test.js` 只能测 `extractModelNames` / `classifyModelNames` 两个纯函数，
文件头的注释明说「测 `readClaudeModelNames` 就得去读用户真实的 `~/.claude/settings.json`，
既不可控，也不该让测试依赖用户的私人文件」。

**还原是本项目里最危险的一段代码**——写错就是毁掉用户的 Claude Code 配置，
而它偏偏是目前最测不了的部分。因此按 `store.js` 的既有范式
（[store.js:59](../../src/main/store.js#L59) 的 `createStore({ dir })`）改造成工厂：

```js
function createSetup({ claudeDir = DEFAULT_CLAUDE_DIR } = {}) { … }
```

保留现有的模块级导出（`previewClaudeSettings` 等）作为默认实例的绑定，
既有调用点与测试不受影响；测试用 `mkdtemp` 造隔离目录。

### 3.5 退出钩子：全部收口到 `before-quit`

**这是第 1 版最严重的错误**：`window-all-closed` 在应用正在退出时**不会发出**
（Electron 文档明说：用户按 Cmd+Q、或有人调了 `app.quit()` 时，应用即将退出，
该事件不触发）。macOS 上最常见的退出方式恰恰是 Cmd+Q —— 挂在那里等于还原从不执行。

```
window-all-closed → 只做 app.quit()（不再承担还原）

before-quit:
  event.preventDefault()
  if (restoreState === 'running') return          // 防重入
  if (restoreState === 'done') { app.exit(0); return }
  restoreState = 'running'
  await restore()            // 失败则按 R10 的退出分支弹框，只给「仍然退出」
  await proxy.stop()         // 带超时，见 3.5.2
  restoreState = 'done'
  app.exit(0)                // ← 用 exit 而非 quit：exit 不触发 before-quit，天然不死循环
```

**不注册 `process.on('SIGINT' / 'SIGTERM')`**：macOS 上从 Finder/Dock 启动的 `.app` 没有控制终端，
收不到 Ctrl+C；系统注销/关机也不是先发 SIGTERM，而是 quit Apple Event（走 `before-quit`）。
这两个处理器对真实用户路径覆盖为零，却会和 Electron 自身的退出流程打架。退出只留一个口子。

#### 3.5.1 为什么必须用 `app.exit()`

`app.quit()` 每次调用都会**先 emit `before-quit`**。若在那里 `preventDefault()` 等用户
在失败弹框上做选择，用户点「仍然退出」时再调 `app.quit()` —— 又一次进入同一个失败还原、
又弹同一个框，形成**退不掉的死循环**。`app.exit(0)` 不触发这些事件，循环不存在。

#### 3.5.2 `proxy.stop()` 必须是有界的

[proxy.js:489-494](../../src/main/proxy.js#L489-L494) 的 `stop()` 只有
`await new Promise((resolve) => server.close(resolve))`：Node 的 `server.close()`
要等**所有已建立的连接结束**才回调，而代理给 Claude Code 服务的那条转发路径**没有任何超时**
（[proxy.js:643](../../src/main/proxy.js#L643) 的 20s setTimeout 只存在于 `testUpstream`）。
用户正开着 Claude Code 会话时退出应用，`close()` 可能永不回调，退出被卡死。

两个修法一起上：

1. `stop()` 里记下 server 引用后立刻置空，并给 `close()` 加超时（如 2s），超时后强制继续；
2. `closeAllConnections()`（Node 18.2+）掐掉存量连接。

#### 3.5.3 顺带要修的代理侧缺陷（审查中发现）

```js
async function start() {
  if (server) return actualPort;          // ← server 已被赋值，actualPort 仍是 null
  server = http.createServer(handleRequest);
  actualPort = await listenWithFallback(...);   // 这里抛错 → server 非 null、actualPort 为 null
}
```

`listenWithFallback` 一旦抛错，`server` 已是非 null 对象。**之后再调 `start()` 会命中第一行，
直接返回 `null`，既不报错也不重新监听** —— R9 的「重试接管」按钮会点不动。
修法：失败时把 `server` 置回 `null`（并 `close()` 掉半开的实例）。

## 4. 边界与风险

| 场景 | 行为 | 是否可接受 |
|---|---|---|
| 接管期间另开一个终端的 Claude Code 会话，然后关掉应用 | 那个会话的下一次请求会失败 | 可接受，但要在确认弹窗里说明「退出会断开正在使用本代理的会话」 |
| `kill -9` / 崩溃 | 文件残留接管配置，Claude Code 连不上 | 下次启动应用即自愈（R3）；残留不会被污染成 `previous`（R6） |
| 用户接入后**再也不打开**本应用 | Claude Code 永久指向死端口 | **本方案最大的残余风险**。缓解：确认弹窗明确告知 + 界面常驻显示「已接管」+ 备份路径可查 + 退出时的失败详情会写进 `lastRestore` |
| 用户在接管期间手改了那两个键 | 还原时跳过该键并告知（R5 第三种情形） | 符合预期 |
| 用户在**两次会话之间**（应用关着）改了配置 | 下次启动接管时被覆盖，但**退出还原到的是这个新值**（`previous` 每次刷新） | 符合预期，这是 R2 的定义 |
| 8787 被占用，代理漂移到 8788 | 写进配置的是 `proxy.baseUrl`（8788），`applied` 同步刷新 | 符合预期 |
| `settings.json` 被外部改坏成非法 JSON | 还原抛错、不写入、按 R10 告知 | 与现有 `readCurrentSettings` 行为一致 |
| 代理未就绪 / 无已激活供应商 | 拒绝接入并说明原因（R7），界面进第二态（R9） | 符合预期 |
| 接入前 `~/.claude/settings.json` 不存在 | 还原后仍然不存在（R2） | 符合预期 |

### 一条不可绕过的规矩

**还原路径必须有单元测试 + 一次真 Electron 端到端验证**。
按项目既有规矩（见前一份 PRD 第 4 节），`npx tsc --noEmit` / `npm run lint` 全绿
**不足以**证明渲染进程或生命周期改动是好的 —— 必须真起 Electron 走一遍
「接入 → 关闭 → 检查文件已还原」。

## 5. 非目标

- **不做托盘常驻**。退出就是退出（[index.js:172-178](../../src/main/index.js#L172-L178)

- **不碰模型映射与代理转发逻辑**。本次只改接管/还原这一条线（3.5.3 的两个 proxy 缺陷除外，
  它们直接影响接管能否工作）。
- **不修「测试」按钮的误报**（探测模型取了 `modelMap` 第一条规则的目标名，
  导致 OpenRouter 地区封锁的 403 被报成「认证失败」）。那是独立缺陷，另行处理。
- 不改 `usage.jsonl`、日志、用量视图。

## 6. 验证方式

### 6.1 单元测试（扩展到 `test/setup.test.js`，全部在 `mkdtemp` 隔离目录上跑）

1. 首次接入：记录 `previous` / `fileExisted`、产生**一个**备份、写入 `applied`
2. 还原：当前值 === `applied` → 回到 `previous`
3. 还原：`previous[key]` 为 `null` → 该键被**删除**
4. 还原：用户手改过 → 该键**不动**，返回值里带标记
5. 还原：当前值 === `previous` → **不写、不告警**（幂等，R5 第二条分支）
6. 还原幂等：连调两次，第二次结果为空且无告警
7. 还原：文件是非法 JSON → 抛错且**不写入**
8. 还原：接入前文件不存在 → 还原后**文件仍然不存在**（R2）
9. 连续两次「启动接管」**不产生新备份**（3.2 的坑）
10. **非接管期间用户改了值 → 启动接管 → 退出还原为该新值**（R2 的定义）
11. **文件里残留 `applied`（模拟 kill -9）→ 启动接管不得把残留记进 `previous`**（R6）
12. 空串 `""` 与「键不存在」要被区分开（3.1 的 falsy 坑）
13. 代理未就绪 / 无已激活供应商 → apply 抛错（R7）
14. `applyClaudeSettings` 抛错时不写 `enabled=true`（R11）

### 6.2 真 Electron 端到端

隔离 `HOME=/tmp/xxx`：

1. 预置一份 `settings.json`（含真实形状的 `ANTHROPIC_BASE_URL` / `AUTH_TOKEN` / `*_MODEL` 键）
2. 起应用 → 走接入流程
3. 读文件：确认两个键被改、模型相关键原样、`~/.claude/` 下**恰好一个**备份
4. **按 Cmd+Q 等价的 `app.quit()` 路径退出**（这一步专门验 3.5 的钩子迁移）
5. **读文件：确认两个键已还原为原值**（本 PRD 的核心断言）
6. 再起一次 → 确认自动接管（R3）；再关 → 再次还原
7. 点「断开接入」→ 确认还原且**再起应用不再接管**（R4）
8. 另跑一遍：**不预置** `settings.json`，接入后退出，确认文件仍不存在

### 6.3 冒烟守护

`scripts/ui-smoke.js` 增一条断言，但**不能自证**（第 1 版的写法是与被测对象同源、
又开局就 reload，等于什么都没测）：

- 读 `~/.claude/settings.json`，断言侧边栏的接管状态行与「文件里两个键是否等于
  `takeover.applied`」一致 —— 以**文件内容**为基准，`enabled` 只作旁证；
- 再补一条**不 reload** 的用例：在页面里点「确认写入」（或「断开接入」）后**立即**读状态行，
  断言两者同步变化 —— 这条才覆盖 R9 要求的刷新路径。

## 9. 实测结论（2026-09-22）

R1–R11 十条**全部落地**，第 7 节执行顺序的 11 步全部走完。本节记录实测数据，

### 9.1 证据

| 检查 | 命令 | 结果 |
|---|---|---|
| 单元测试 | `npm test` | **123 通过 / 0 失败**（519 ms）。其中接管/还原 18 条、代理准入与生命周期 8 条、store 9 条 |
| 类型 | `npx tsc --noEmit` | 干净 |
| 规范 | `npm run lint` | 干净，零告警 |
| 真 Electron 端到端 | `npm run e2e` | **5 个场景全部通过** |

`npm run e2e` 本次跑出的关键断言（原文摘录）：

```
【场景 1】接入 → 退出自动还原
  ✓ 恰好产生一个备份（实际 1 个）      ✓ settings.json 的权限仍是 0600
  ✓ 记下的 previous 是用户原值
  — 应用已退出，检查还原 —
  ✓ 退出后 ANTHROPIC_BASE_URL 已还原（实际 https://api.deepseek.com/anthropic）
  ✓ 退出后模型相关配置仍然原样         ✓ 退出还原没有再产生备份
【场景 2】重开应用 → 自动接管          ✓ 无需任何点击即处于「已接管」
【场景 3】断开接入                     ✓ 授权记忆被清除

【场景 5】接入前没有 settings.json     ✓ 退出后文件被删掉，回到「接入前不存在」的状态
```

### 9.2 一个**真实**覆盖到的分支：端口漂移

跑 E2E 时用户的实例正占着 8787，于是测试实例顺延到了 **8788**：

```
· 本次代理实听地址：http://127.0.0.1:8788
· 8787 被占用、代理已漂移 —— 写进配置的必须是实听地址，这正是要验的分支
```

这条断言（R7 的第二段注记、3.1 的第二条注意）**不是靠构造出来的** ——
它是真实环境里自然发生的，因此比任何人为 mock 都可信。
如果 `applied.ANTHROPIC_BASE_URL` 误取了 `store.getSettings().port`，
R5 的「等于 `applied`」判定会立即失配，场景 1 的还原断言会红。它绿了。

### 9.3 与设计的偏离：本地准入凭证不在本 PRD 范围内

本 PRD 写于审计之前，第 3.1 节的示例里写进 Claude Code 的 token 是公开常量
`cc-nbproject-managed`。**审计的 H6 把它推翻了** —— 公开常量等于把门钥匙贴在门上，
同机任何进程抄走就能借代理消耗用户的真实 key。

现在写进去的是 `store.getLocalToken()` 生成的**每次安装随机 32 字节凭证**，
代理侧由 `holdsLocalToken()` 校验。这条**不属于 R1–R11**，是 H6 的处置，
但它改变了 3.1 里那个字段的取值来源。详见
[审计发现与处置 § H6](../审计发现与处置.md#h6--同机任何进程都能白嫖用户的真实-key)。

3.1 的 jsonc 示例已相应标注，不再是可直接照抄的规格。

### 9.4 实施中发现的**设计之外**的缺陷

三条，都不在 R1–R11 里，是做的过程中撞出来的。完整说明见
[审计发现与处置](../审计发现与处置.md) 的「同轮一并修复的其它问题」：

| 缺陷 | 为什么必须在这里修 |
|---|---|
| `listenWithFallback` 回退时堆积死 `listening` 监听器 | 是 3.5.3 那个 `start()` 缺陷的同一段代码，改一处必须看全 |
| `previewClaudeSettings` 预测的备份路径与实际的不是同一个 | 正是 3.2 点名的坑，修 3.2 时顺带钉死 |
| 落败实例的退出分支会生成 `profiles.json` | R8 要求「落败实例不做任何事」，而它当时会写文件 |

## 附：第 1 版被推翻的设计与原因

第 1 版 PRD 写完后的对抗性审查（40 个 agent、19 条发现、逐条派独立 agent 读源码核实，
27 条成立 / 9 条驳回）推翻了它的两处**根本性**设计。记在这里，避免以后重蹈：

1. **还原挂在了 `window-all-closed`**。该事件在应用正在退出时不触发（Cmd+Q 正是如此），
   等于方案 A 在 macOS 最常见的退出路径上从不生效。→ 已改为 3.5 的单口 `before-quit`。
2. **`previous` 被定义为「首次接入时的快照」**。用户关着应用时改了配置，下次启动接管后
   再退出，会把用户的新配置覆盖回首次接入那天的旧值 —— 静默丢弃用户的修改，
   正是本工具最该避免的事。→ 已改为「本次接管前的实际值」，每次刷新（3.1）。

另有六条会导致「配置永久卡在死端口」「退不掉的死循环」「单实例互踩」的缺陷、
四条第 1 版自己写错的代码事实（如 R7 声称「端口被占代理起不来」——
实际 [proxy.js](../../src/main/proxy.js) 会自动换端口），以及两条可测性问题
（冒烟断言自证、界面状态无刷新路径），均已并入上文。
