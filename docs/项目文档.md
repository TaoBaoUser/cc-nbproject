## 1. 项目是什么、解决什么问题

### 1.1 一句话

**本地反向代理 + 桌面控制台，让 Claude Code 切换 API 供应商时不需要重启。**

### 1.2 它解决的问题：为什么换供应商一定要重启

在 Claude Code 里换一个 API 供应商，通常意味着手工编辑 `~/.claude/settings.json` 的 `env` 块，
**然后重启 Claude Code**。

而「必须重启」这件事绕不过去：Claude Code 提供了动态获取 **API key** 的钩子
（`apiKeyHelper`），但**没有任何机制能动态改变 base URL**。只要 base URL 会变，就一定要重启。

### 1.3 做法：让 base URL 永远不变

本项目换一个思路 —— **不去改 base URL，而是让 base URL 指向一个恒定的本地地址**。

```
   Claude Code
        │  ANTHROPIC_BASE_URL = http://127.0.0.1:8787-8807
        │  （只写一次，之后永不修改；8787 被占则自动顺延）
        ▼
   ┌──────────────┐
   │ cc-nbproject │  按当前选中的供应商转发
   └──────────────┘
      │      │      │
      ▼      ▼      ▼
  DeepSeek  智谱   Kimi
```

切换供应商 = 改变**本地代理的路由目标**。Claude Code 全程无感知，
**正在运行的会话不受影响**。

这个「路由目标」是一个每次请求都会调用的函数（`getActiveProfile`），
所以切换只需要改动配置里的 `activeId` —— 既不重启 Claude Code，也不重启代理本身。

### 1.4 功能一览（v0.1）

| 功能           | 说明                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 供应商增删改查 | 一键切换，零重启                                                                                                       |
| 连接测试       | 发一个极小请求，验证 key 有效性并测出延迟                                                                              |
| **接管与还原** | 点一次「确认接管」即长期记住；此后开应用自动接管、**关应用自动还原**；随时可「断开接入」                               |
| 实时请求日志   | 每个请求走了哪个供应商、状态码、耗时                                                                                   |
| 用量统计       | token 消耗与请求数                                                                                                     |
| 模型映射       | 不同供应商对同一模型的叫法不同（如 OpenRouter 要求 `vendor/model`），按「源=目标」逐行填写，未命中的模型名**原样转发** |
| 模型列表拉取   | 从供应商拉取可选模型 ID 自动预填映射（**辅助功能，不是依赖**）                                                         |
| 系统代理支持   | 上游请求自动走 macOS 的系统代理设置                                                                                    |

**v0.1 明确不做**：故障转移、系统托盘、应用打包分发、配置加密。

> 「模型列表拉取」为什么只是辅助：Claude Code 的兼容接口规范里**并没有** `/v1/models`，
> 不少供应商没有这个端点。手动填写映射永远可用。

## 2. 快速上手

### 2.1 环境要求

- **Node.js ≥ 22.12**（见 `package.json` 的 `engines`）
- 仓库里有 `.nvmrc`，`nvm use` 即可对齐

> 为什么卡在 22：`npm run smoke` 依赖 Node 22 才有的**全局 `WebSocket`**，
> 这是它不引入 puppeteer 就能驱动 Chrome DevTools Protocol 的前提。

### 2.2 安装

```bash
git clone https://github.com/TaoBaoUser/cc-nbproject.git
cd cc-nbproject
npm install
```

> **⚠️ 关于 Electron 二进制**
> `electron@44` 的 npm 包**不再自带 `postinstall` 脚本**，二进制需要单独下载。
> 本项目的 `package.json` 已补上这一步，正常情况下 `npm install` 会自动完成。
> 若安装后遇到 `Cannot find module ... path.txt`，手动执行：
>
> ```bash
> node node_modules/electron/install.js
> ```
>
> 国内网络建议走镜像：
>
> ```bash
> ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ node node_modules/electron/install.js
> ```

### 2.3 第一次运行

```bash
npm run build    # ⚠️ 必须先构建
npm start        # 启动应用
```

> **干净克隆直接 `npm start` 会白屏** —— `dist/` 在 `.gitignore` 里，不存在。

首次启动会引导你：

1. 添加至少一个供应商（填 base URL 和 API key）
2. 授权本工具接管 Claude Code 配置（**会先自动备份 `settings.json`**）
3. 完成 —— 之后切换供应商都不再需要重启 Claude Code

### 2.4 接管是双向的（使用者视角）

| 时机           | 行为                                         |
| -------------- | -------------------------------------------- |
| 点「确认接管」 | 备份（**仅首次**）→ 写入配置，记住你原本的值 |
| 之后每次启动   | 自动接管，不再询问                           |
| **每次退出**   | **自动还原成你原来的配置**                   |
| 点「断开接入」 | 还原 + 清除授权记忆（此后启动不再接管）      |

还原只针对 `ANTHROPIC_BASE_URL` 与 `ANTHROPIC_AUTH_TOKEN` 两个键，
模型名、权限、hooks 等一概不碰；**你自己手改过的键不会被覆盖**，应用会告诉你哪一项被跳过了。

> **如果你以后不再打算打开本应用，请先点「断开接入」。**
> 应用关着的时候代理是不运行的，此时 Claude Code 会指向一个没人监听的端口。

### 2.5 命令速查

```bash
# --- 开发 ---
npm run dev          # Vite dev server + Electron（改渲染进程时用，有热更新）
npm run build        # 构建渲染进程到 dist/

# --- 验证（三级，见第 6 章）---
npm run verify       # 第 1 级：类型检查 + lint + 单元测试（一键）
npm test             # 只跑单元测试（node --test）
npm run typecheck    # 渲染进程 + 主进程两份 tsconfig
npm run lint         # ESLint
npm run format       # Prettier 写入
npm run format:check # Prettier 只查不写

npm run e2e          # 第 2 级：真 Electron 端到端（接管 → 退出 → 还原）
npm run smoke        # 第 3 级：真实窗口冒烟（需先手动起调试端口，见 6.1）
```

## 3. 架构

### 3.1 全景

```
┌─────────────────────── Electron 应用 ───────────────────────┐
│                                                              │
│  主进程 (src/main)                    渲染进程 (src/renderer) │
│  ┌────────────────────┐               ┌──────────────────┐   │
│  │ index.js  装配/生命周期│              │ App.tsx          │   │
│  │  ├ proxy.js  ★代理   │◄── IPC ──────┤  hooks/          │   │
│  │  ├ setup.js  ★接管   │  (白名单)     │  views/          │   │
│  │  ├ store.js  配置    │               │  components/     │   │
│  │  ├ models.js 模型列表 │               │  modals/         │   │
│  │  └ usage.js  用量    │               └──────────────────┘   │
│  └────────────────────┘                        ▲              │
│           ▲                                    │              │
└───────────┼────────────────────────────────────┼──────────────┘
            │ 转发                                │ contextBridge
            │                                     │ (preload/index.js)
   ┌────────┴─────────┐                  ┌────────┴─────────┐
   │ 上游供应商 API    │                  │ Claude Code      │
   │ (DeepSeek/Kimi…)  │                  │ (命令行/IDE 里的) │
   └───────────────────┘                  └──────────────────┘
                                            ANTHROPIC_BASE_URL
                                            = 本机代理
```

### 3.2 两条硬边界

**边界一：代理跑在主进程，不在渲染进程。**

渲染进程是沙箱化的浏览器环境（`sandbox: true`、`nodeIntegration: false`、
`contextIsolation: true`），不适合监听端口；主进程才是完整的 Node 运行时。
这条边界是理解 Electron 安全模型的关键。

**边界二：`proxy.js` / `setup.js` / `store.js` / `models.js` / `usage.js` 都不依赖 Electron。**

这是 `npm test` 能在**几百毫秒内**跑完上百个用例、完全不需要 GUI 的唯一原因。
依赖方向是单向的：

```
renderer (React, 无 fs/net)
    │  window.ccnb.*  ← preload 白名单
    ▼
preload (contextBridge)
    │  ipcRenderer.invoke('域:动作')
    ▼
main/index.js  ← 唯一的装配点：装配 + IPC 编排 + 生命周期
    ├── proxy.js        纯 Node，零 Electron 依赖
    ├── proxy-agent.js  纯 Node
    ├── setup.js        纯 Node（只 fs）
    ├── store.js        纯 Node（只 fs）
    ├── models.js       纯 Node
    └── usage.js        纯 Node（只 fs）
```

**为什么坚持工厂函数而不是模块级单例**：`createStore({ dir })`、`createSetup({ claudeDir, localToken })`、
`createProxy({...})`、`createUsageStore({ dir })`、`createModelFetcher({...})` 全部可注入路径或依赖。

因为**必须能被测试的恰好是最危险的那段代码** —— 还原逻辑写错就毁掉用户的 Claude Code 配置，
而它偏偏是「路径写死在模块顶层时最测不了」的部分：想测一次就得去读写用户的私人文件。
注入之后，测试可以用 `mkdtemp` 把它测透。

### 3.3 一次请求的完整路径

```
Claude Code
  │ POST http://127.0.0.1:8787/v1/messages
  │ Authorization: Bearer <localToken>
  ▼
proxy.handleRequest
  ├─ 1. 准入校验  holdsLocalToken(req, getLocalToken())
  │       不过 → 401 {"type":"unauthorized"}，**不打上游**
  ├─ 2. getActiveProfile()  （包在 try/catch 里）
  │       抛错 → 500 config_unreadable；为 null → 503 no_active_profile
  ├─ 3. 解析 profile.baseUrl，拼路径 basePath + clientReq.url
  │       baseUrl 非法 → 500 invalid_base_url
  ├─ 4. 选传输：需要走系统代理时用 proxy-agent.js，否则直连
  ├─ 5. 模型映射（仅命中时才重新序列化请求体）
  │       rewriteModel() 命中 → 改写 model 字段；未命中 → 原样透传
  ├─ 6. 换掉凭证：发往上游的是 profile.apiKey，客户端的凭证被丢弃
  ├─ 7. 流式判定（content-type 含 text/event-stream）
  │       ├─ 是 → SSE：逐块透传，不缓冲；顺路抽 usage
  │       └─ 否 → 收全再转发，从响应体抽 usage
  └─ 8. onUsage / onRequest 回调 → index.js 广播到界面
```

**为什么模型映射「未命中就返回 null」**：命中才需要重新序列化整个请求体。
未命中时把原始 Buffer 直接转发，既省一次解析，也保证非 JSON 请求体
（比如某些附件流）不被破坏。

### 3.4 模块逐个说明

#### `src/main/index.js` —— 装配与生命周期

**职责**：创建窗口、装配各模块、注册全部 IPC、编排接管/还原、管理退出。

| 不变量                                                    | 为什么                                                                       |
| --------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 单实例锁在**模块顶层**判定，落败分支不做任何还原          | 两个实例会同时持有接管状态，先退出的那个执行还原会把仍在运行的实例的接管撤掉 |
| `bootstrap()` 包裹全部副作用                              | 失败分支不许生成 `profiles.json` —— 一个「什么都不做」的退出不该有副作用     |
| 接管/断开用 `takeoverBusy` 串行，后来者直接拒绝（不排队） | 两者都是「读-算-写」复合动作，交错会写出不一致状态                           |
| 接管失败时**绝不**写 `enabled = true`                     | 否则留下「界面说已接管、文件其实还是原样」的半接管状态                       |
| 断开时**先还原、后清授权记忆**                            | 反过来做，还原失败时用户会同时失去重试机会与 `previous`/`backupPath`         |
| 还原只在 `before-quit` 做一次，然后 `app.exit(0)`         | 见 4.6                                                                       |

#### `src/main/proxy.js` —— 代理核心

**职责**：`http.createServer` + 转发 + SSE + 用量提取 + 连接测试。

**对外**：`createProxy({ getActiveProfile, getLocalToken, onUsage, onRequest, host, port })`
→ `{ start, stop, port, host, baseUrl }`。

**三个容易写错的点**：

- **`baseUrl` 是 getter**，取自实听端口。端口被占时会向上顺延（8787→8807，最多 20 次）。
  任何需要写地址给用户的地方都必须用它，**不能写死 8787**。
- **`stop({ timeoutMs })` 有超时上界**。`server.close()` 要等所有连接结束，
  而转发路径没有超时 —— 用户开着 SSE 会话时这个等待没有上界，而退出流程会 `await` 它，
  表现为「关掉窗口后应用再也退不掉」。
- **`start()` 失败时必须把 `server` 清回 `null`**。否则下一次 `start()` 会命中
  `if (server) return actualPort` 直接返回 `null` —— 不报错也不重试。

#### `src/main/setup.js` —— 唯一会改用户文件的模块

**对外**：`createSetup({ claudeDir, localToken })` →
`{ claudeDir, settingsPath, previewClaudeSettings, applyClaudeSettings,
   restoreClaudeSettings, readClaudeModelNames, readCurrentSettings, detectManagedConflict }`

**两条贯穿全文件的规矩**：

1. **预览与应用必须分开**，中间由用户显式确认。任何静默修改都是不可接受的。
2. **接管必须是双向的**。只接不管，用户关掉应用后 Claude Code 就指向一个没人监听的端口。

**受管键只有两个**：`ANTHROPIC_BASE_URL`、`ANTHROPIC_AUTH_TOKEN`。
模型相关键（`ANTHROPIC_MODEL` 等）是用户对自己所用模型的配置，与走不走代理无关。

#### `src/main/store.js` —— 配置持久化

读写 `~/.cc-nbproject/profiles.json`，**原子写入**（tmp → rename → chmod），权限 `0600`。

**为什么原子**：进程在写入中途崩溃（或磁盘写满）时，目标文件会变成半截 JSON，
下次启动 `JSON.parse` 抛错，工具彻底起不来 —— 而那里面有用户所有的 API key。

#### `src/main/proxy-agent.js` —— 上游请求走系统代理

Node 的 `http`/`https` 既不读 macOS 的「网络」设置，也不读 `HTTPS_PROXY`
（除非显式开启），所以主进程的请求永远直连。上游按来源地区限制时
（例如 OpenRouter 的 `openai/*` 一族），用户明明开着代理却连不上。

macOS 走 `scutil --proxy` 探测（结果缓存 60 秒 —— 系统代理可能随时开关）；
**回环与内网地址永远直连**，把它们交给代理是错的。

#### `src/main/models.js` / `usage.js`

- `models.js`：从供应商拉 `/v1/models` 并归一化（三种响应形状都容忍），带缓存
  （OpenRouter 有 446 个模型）。失败要给出**可读的分类**（`empty` / `auth_failed` /
  `network_error`…），不要只丢一个 HTTP 状态码。
- `usage.js`：`usage.jsonl` 的追加与聚合。选 JSONL 而非 JSON 数组是为了 **O(1) 追加**；
  读取时最多回看 50000 行，避免文件无限增长拖慢读取。

#### `src/preload/index.js` —— 白名单

**关键点：白名单而非透传。** 绝不能写成
`exposeInMainWorld('ipcRenderer', ipcRenderer)` —— 那等于把整个 IPC 面暴露给页面脚本，
而页面会显示来自 API 响应的内容。

#### `src/renderer/` —— React 界面

```
App.tsx            顶层：视图切换 + 模态框开关
hooks/             每个 hook 对应一块主进程状态
  useProfiles     供应商列表
  useProxyStatus  代理运行状态
  useClaudeStatus 接管三态
  useLogs         实时日志（订阅 log:event）
  useUsage        用量
views/             ProvidersView / ProviderCard / LogsView / UsageView
components/        Sidebar / ModelPicker / Combobox
modals/            ProfileModal / SetupModal
describe.ts       把连接测试与模型拉取的原始结果翻译成用户能照着做的话
types.ts          ★ 所有跨进程数据结构的唯一来源
model-map.js      模型映射文本的解析（**刻意留在 .js**：要能被 node --test 直接 require）
```

**`describe.ts` 为什么单独存在**：主进程返回的是分类码，界面上要变成
「你的 key 无效，请检查供应商后台」这样的话。翻译逻辑集中在 `describe.ts`，
视图里不该出现 `if (kind === 'auth_failed')`。

### 3.5 IPC 契约（完整清单）

渲染进程能做的事情**只有下面这些**。新增能力必须**四处同步**，
缺一不可（这是本仓库最容易漏的一处）：

1. `src/main/index.js` 的 `ipcMain.handle`
2. `src/preload/index.js` 的白名单方法
3. `src/renderer/ccnb.ts` 的方法签名
4. `src/renderer/types.ts` 的数据结构

| 通道                | preload 方法               | 用途                            |
| ------------------- | -------------------------- | ------------------------------- |
| `profiles:list`     | `listProfiles()`           | 供应商列表 + 当前激活项         |
| `profiles:add`      | `addProfile(payload)`      | 新增                            |
| `profiles:update`   | `updateProfile(id, patch)` | 修改（服务端有字段白名单）      |
| `profiles:remove`   | `removeProfile(id)`        | 删除                            |
| `profiles:activate` | `activateProfile(id)`      | 切换（**零重启的核心**）        |
| `profiles:test`     | `testProfile(id)`          | 连接测试                        |
| `usage:summary`     | `getUsageSummary(range)`   | 用量聚合                        |
| `usage:recent`      | `getRecentUsage(limit)`    | 最近流水                        |
| `proxy:status`      | `getProxyStatus()`         | 代理运行状态                    |
| `models:list`       | `listModels(payload)`      | 拉取供应商模型列表              |
| `claude:modelNames` | `getClaudeModelNames()`    | 读 Claude Code 实际会发的模型名 |
| `claude:status`     | `getClaudeStatus()`        | 接管三态                        |
| `claude:preview`    | `previewClaudeSettings()`  | 接管预览（**不写任何东西**）    |
| `claude:takeover`   | `takeoverClaude()`         | 执行接管                        |
| `claude:disconnect` | `disconnectClaude()`       | 断开接入（还原 + 清记忆）       |

**反向推送**：主进程 → 渲染进程只有一条广播通道 `log:event`
（`kind: 'usage' | 'request' | 'switch'`），经 `onLogEvent(callback)` 订阅，
返回取消订阅函数。

> **契约没有自动化校验。** `preload/index.js` 虽然在 `tsconfig.main.json` 的 `include`
> 范围内，但它是 `.js` 且**没有 `// @ts-check`**，因此实际不被检查（见 6.7）。
> 改名等于静默改成运行时 `TypeError`。改 IPC 时请**手工**逐一核对上面四处，并跑 `npm run e2e`。

### 3.6 文件与数据的形状

| 路径                                   | 是什么                                                | 权限                |
| -------------------------------------- | ----------------------------------------------------- | ------------------- |
| `~/.cc-nbproject/profiles.json`        | 供应商列表 + 设置 + 接管状态 + 本地准入凭证           | `0600`，目录 `0700` |
| `~/.cc-nbproject/usage.jsonl`          | 用量流水，每行一条 JSON                               | `0600`              |
| `~/.claude/settings.json`              | **用户的** Claude Code 配置。本工具唯一会改的用户文件 | `0600`              |
| `~/.claude/settings.json.bak.<时间戳>` | 首次接管前自动备份，**只产生一次**                    | —                   |

```jsonc
// ~/.cc-nbproject/profiles.json
{
  "version": 1,
  "activeId": "…",              // 当前激活的供应商
  "profiles": [ { "id", "name", "baseUrl", "apiKey", "modelMap", "createdAt" } ],
  "settings": {
    "port": 8787,               // 起始端口，被占则向上顺延，最多 20 次
    "localToken": "…64 位十六进制…",   // 本机代理的准入凭证，见第 5 章
    "takeover": null            // 接管状态快照；null = 从未接管过
  }
}
```

## 4. 接管与还原

**这是本仓库最需要小心的一条线。** 它直接改写用户的 `~/.claude/settings.json`。

### 4.1 语义：一次授权，长期记住；开应用才生效，关应用自动还原

| 时机               | 行为                                                               |
| ------------------ | ------------------------------------------------------------------ |
| 用户点「确认接管」 | 备份（仅首次）→ 写入两个受管键 → 记下 `previous`（接管前的真实值） |
| 应用启动           | 若此前授权过，**自动**再接管一次（不再询问），同时刷新 `previous`  |
| 应用退出           | **自动还原**成接管前的样子                                         |
| 点「断开接入」     | 还原 + 清除授权记忆（此后启动不再自动接管）                        |

### 4.2 持久化形状

```jsonc
// profiles.json 的 settings.takeover
{
  "enabled": true, // 用户授权过长期接管
  "applied": { "ANTHROPIC_BASE_URL": "http://127.0.0.1:8788", "ANTHROPIC_AUTH_TOKEN": "…" },
  "previous": {
    "ANTHROPIC_BASE_URL": "https://api.deepseek.com/anthropic",
    "ANTHROPIC_AUTH_TOKEN": "sk-…",
  },
  "fileExisted": true, // 接入前 settings.json 是否存在
  "backupPath": "/Users/…/settings.json.bak.2026-09-22T…",
  "residualDetected": false, // 是否发现过我们上次留下的残渣
  "lastApply": { "ok": true, "at": "…", "reason": null },
  "lastRestore": { "ok": true, "at": "…", "reason": null },
}
```

**`previous[key] === null` 的含义是「该键原本不存在」**，还原时要把它**删掉** ——
不是写成空串。

### 4.3 三态：`off` / `active` / `pending`

```
        ┌──────────────────────┐
        │ off  未接管           │
        └──────────┬───────────┘
                   │ 用户点「确认接管」
                   │ 准入检查：代理在监听？有激活的供应商？
                   ▼
        ┌──────────────────────┐
        │ active 已接管         │◄──── 应用每次启动自动回到这里
        │ 文件里确实是我们写的值  │
        └──────────┬───────────┘
                   │
        ┌──────────┴───────────┐
        │ 应用退出 → 还原        │──► 文件回到 previous，enabled 保留
        │ 点「断开接入」→ 还原    │──► 文件回到 previous，takeover 清空
        └──────────────────────┘

        ┌──────────────────────┐
        │ pending 已授权未生效   │  授权过，但本次没写进去
        │ （代理没起来 / 写失败） │  界面要显示 lastApply.reason
        └──────────────────────┘
```

**`active` 与 `pending` 的区分是界面上的要害。** 两者都「授权过」，差别在于
**本次到底写没写进用户的文件**。把 `pending` 显示成「已接管」会让用户在
Claude Code 连不上时完全摸不着头脑 —— 界面说一切正常，配置里却还是旧地址。

判定**以文件内容为准**（`buildTakeoverStatus` 逐键比对 `takeover.applied`），
`enabled` 只作旁证。

### 4.4 还原的三态判定（`restoreClaudeSettings`）

| 当前值               | 含义                     | 动作                                       |
| -------------------- | ------------------------ | ------------------------------------------ |
| 等于 `applied[key]`  | 是我们写的，没被动过     | 回滚为 `previous[key]`（为 `null` 则删键） |
| 等于 `previous[key]` | 已是目标状态（刚还原过） | 不写、不标记（**幂等**）                   |
| 其它                 | 用户自己改过             | 保持不动，标记进 `externallyModified`      |

第二条分支是幂等的落点。没有它，第二次还原会把「我们刚写回去的原值」
误报成「用户改过」，产生假告警。

另外两处极易写错的地方：

| 位置                                     | 坑                                                                                             |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `looksLikeOurOwnValue`                   | 判定「这个值是不是我们自己写的」。**宁可不认，也不能误认** —— 误认会把用户真实配置当成残渣丢掉 |
| `applyClaudeSettings` 的 `previous` 计算 | 残渣**绝不能**记进 `previous`，否则还原会把死值写回给用户                                      |

### 4.5 写序与并发

**写序不许反**：`applyClaudeSettings` 成功落盘**之后**才能写 `takeover.enabled = true`。
反过来会留下「界面说已接管、文件其实还是原样」的半接管状态：
退出还原又因为文件里的值不等于 `applied` 而跳过 —— 两头都对不上，
用户看到的却是一切正常。

**接管与断开必须串行**（`withTakeoverLock`）。两者都是「读文件 → 算 → 写文件 → 写状态」
的复合动作，交错执行会写出不一致的状态。后来者直接拒绝，**不做排队** ——
这类操作本来就该由用户一个一个点。

### 4.6 退出路径为什么只留一个口子

```js
app.on('before-quit', async (event) => {
  if (quitHandled) return;
  event.preventDefault();
  // …还原（含失败时告知用户）…
  await proxy.stop();
  quitHandled = true;
  app.exit(0); // 用 exit 而不是 quit：quit 会重新触发 before-quit → 死循环
});
```

**三个不能改的地方**：

1. **`window-all-closed` 绝对不能挂还原。** 它在「应用正在退出」时**根本不触发**，
   而 macOS 上最常见的退出路径 Cmd+Q 正是「应用正在退出」。挂在它上面等于
   在最主要的路径上从不执行 —— 而开发者在本地点关闭按钮测试时**它会正常工作**。
2. **不注册 `SIGINT` / `SIGTERM`。** macOS 上从 Finder/Dock 启动的 .app 没有控制终端，
   收不到 Ctrl+C；系统注销/关机走的是 quit Apple Event（即 `before-quit`）。
   那两个处理器对真实用户路径**覆盖为零**，却会和 Electron 自己的退出流程打架。
3. **用 `app.exit(0)` 而不是 `app.quit()`。** 后者会重新触发 `before-quit`，
   若还原失败就会再弹一次同样的框，形成退不掉的死循环。

**还原失败时**（`R10` 的处置）：窗口可能已全关、应用不在前台，弹框会被压在别的应用后面，
所以**只给一个动作**（「仍然退出」）—— 不点也不至于退不出去。弹框里必须写明
备份文件路径与手动恢复方法。

### 4.7 准入条件（接管前必须成立的两条）

1. **代理确实在监听**，且拿得到**实听**地址（`proxy.baseUrl`）。
2. **有已激活的供应商** —— 否则代理对每个请求空转。

第一条同时挡掉了一个会实际伤到用户的故障：代理启动失败时，
**绝不能**拿一个兜底地址去写用户配置。地址一律取自 `proxy.baseUrl`。

## 5. 安全模型

### 5.1 威胁模型：防的是谁

本工具在本地运行，处理的是**用户真实的 API key**，并且会**改写用户的配置文件**。
需要防的是：

| 威胁                       | 本项目的应对                                     |
| -------------------------- | ------------------------------------------------ |
| 同机其它进程白嫖用户的 key | 本地准入凭证（见 5.3）                           |
| 同机其它用户读取 key       | 文件权限 `0600` / 目录 `0700`                    |
| 界面里混入恶意脚本         | 渲染进程沙箱 + preload 白名单                    |
| 写坏用户配置               | 预览/应用分离 + 备份 + 三态还原                  |
| 崩溃导致配置留在半接管态   | 见 [8.2](#82-事故档案给接管与还原这个模块的评审) |

**不在威胁模型内**：能读 `~/.cc-nbproject/profiles.json` 的本机用户 ——
他本来就已经拿到了所有真实 key（凭证与 key 同存于此，不增加新的暴露面）。

### 5.2 密钥存在哪

- API key **以明文存储在 `~/.cc-nbproject/profiles.json`**，依靠文件权限 `0600` 保护。
- v0.1 **不做自研加密** —— 加密所需的主密钥同样得存在本地，只是把问题挪了一层。
  后续计划接入系统钥匙串（macOS Keychain 等）。
- 接管时写进 Claude Code 的 `ANTHROPIC_AUTH_TOKEN` **不是用户的真实 key**，
  而是下面这个准入凭证。本工具**替代** Claude Code 保存真实 key。

### 5.3 本地准入凭证（`localToken`）

代理监听 `127.0.0.1`，但**「本机」不等于「本用户」**：同机任何进程、任何账户，
只要能连 `127.0.0.1:8787`，就能让代理拿**用户真实的 API key** 去发请求并计费 ——
而代理的转发逻辑刻意丢弃客户端凭证、无条件换成 `profile.apiKey`（这正是「零重启切换」的实现方式），
于是它同时变成了一个**敞开的中转站**。

| 环节 | 位置                        | 行为                                                            |
| ---- | --------------------------- | --------------------------------------------------------------- |
| 生成 | `store.getLocalToken()`     | 32 字节随机数的十六进制（64 位），首次调用时生成并落盘          |
| 写入 | `setup.buildNextSettings()` | 接管时写进 `ANTHROPIC_AUTH_TOKEN`                               |
| 校验 | `proxy.holdsLocalToken()`   | 只认它：`Authorization: Bearer <token>` 或 `x-api-key: <token>` |

**绝不用固定常量。** 早期版本写的是公开占位符 `cc-nbproject-managed` ——
那等于把门钥匙公开贴在门上，任何进程照抄即可。老安装的残渣会被
`looksLikeOurOwnValue` 认作「我们自己留下的」，在下一次接管时被正确覆盖，
且**不会被误记进 `previous`**。

### 5.4 渲染进程的隔离边界

```js
webPreferences: {
  contextIsolation: true,   // preload 与页面脚本运行在隔离的 JS 上下文中
  nodeIntegration: false,   // 页面无法直接 require 任意 Node 模块
  sandbox: true,            // 渲染进程运行在系统沙箱里
}
```

**这三项缺一不可**，且 `contextBridge` 必须是**白名单**（见 3.5 的清单）。

此外：外部链接交给系统浏览器（`setWindowOpenHandler` 返回 `deny`），不在应用内打开。

### 5.5 已知的暴露面（诚实清单）

以下是**当前版本已知、尚未处理**的暴露面，按严重程度排列。评审时请重点看这里。

| 暴露面                                 | 说明                                                                                                                                  | 影响                                                                  |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `claude:status` 返回的 `previous` 字段 | 含用户接管前的真实 `ANTHROPIC_AUTH_TOKEN`，经 IPC 送到渲染进程，而**界面没有任何一处使用它**（`types.ts` 里有类型定义，视图里零引用） | 纯粹的多余暴露，应当从返回值中移除                                    |
| 用户真实 API key 常驻渲染进程          | `profiles:list` 返回完整 profile（含 `apiKey`），因为编辑框要显示、ModelPicker 要用                                                   | 渲染进程一旦被注入，key 即可被读取。当前 sandbox + 白名单是其唯一防线 |
| `models:list` 的出网参数来自渲染进程   | `baseUrl` 与 `apiKey` 由页面传入，主进程原样用于出网请求                                                                              | 构成「可携带 key 的任意出网请求」原语                                 |
| 备份文件没有显式 `chmod`               | 权限收紧只覆盖了原子写出的三处；`settings.json.bak.*` 没有显式设权限，也没有测试钉死                                                  | 备份里是用户的真实 key                                                |
| 缺少准入凭证时是「放行」               | `proxy.js` 的 `if (localToken && !holdsLocalToken(...))` —— `getLocalToken()` 返回空时**不做任何校验**                                | 安全默认值方向反了，应为「拒绝」                                      |
| 窗口导航面未收口                       | 没有 `will-navigate` 防护，`openExternal` 不校验协议                                                                                  | 低危，但值得补                                                        |

> **另有一处高危崩溃路径**：`proxy.js` 的准入校验里 `getLocalToken()` **没有 try/catch**，
> 而它同样会读 `profiles.json`。文件损坏时异常会穿透 http 监听器、带崩整个主进程 ——
> 这正是 [8.2](#82-事故档案给接管与还原这个模块的评审) 里 H1 修复过的同类问题，
> 但当时只修了 `getActiveProfile()`，**漏掉了排在它前面的这一步**。

## 6. 开发、测试与验证

### 6.1 三级验证（不可跳级）

| 级别 | 命令             | 覆盖什么                                                         | 什么时候跑                       |
| ---- | ---------------- | ---------------------------------------------------------------- | -------------------------------- |
| 1    | `npm run verify` | 类型、规范、纯逻辑、文件读写（隔离目录）、代理转发（本地假上游） | **每次改动**                     |
| 2    | `npm run e2e`    | **真 Electron**：接管 → 校验文件 → 真实退出路径 → 校验还原       | 改 `index.js` 生命周期或渲染进程 |
| 3    | `npm run smoke`  | **真实窗口**：连你正在用的实例去点界面                           | 改界面交互                       |

第 1 级展开就是：`npm run typecheck && npm run lint && npm test`。

**第 2 级要单独起一个终端**（或者用 `npm run e2e`，它自己起）：

```bash
# 第 3 级需要先手动带调试端口启动应用
env -u ELECTRON_RUN_AS_NODE npx electron . --remote-debugging-port=9222
# 另一个终端
npm run smoke
```

### 6.2 一条不可绕过的规矩

> **`tsc` / `lint` / 单测全绿，证明不了渲染进程能渲染，也证明不了生命周期钩子会触发。**

这个仓库已经因此吃过两次亏：

- `.modal-root` 的 `display: flex` 压掉了 `hidden` 属性依赖的 UA 样式 → 遮罩层常驻，
  界面全灰、点不动
- 函数少传参数 → 一打开编辑框就 `TypeError`

两次都是「代码根本没跑到过」，而 **ESLint 看不出来**。

改渲染进程或 `index.js` 后**必须真起一个 Electron**。别用「构建成功」交差。

### 6.3 `npm run e2e` 到底验了什么

`scripts/e2e/run.js` 在 `mkdtemp` 造出的**隔离 HOME** 上启动**生产入口**
（`scripts/e2e/app/main.js` → `src/main/index.js`，一行都不替换），
用 CDP 驱动界面走完「接管 → 校验文件 → 用真实退出路径关掉 → 校验文件已还原」，
共 5 个场景。

**它专门验两件静态检查永远验不了的事**：

1. 渲染进程真的渲染出来了（不是白屏）
2. `before-quit` 真的会触发、`app.exit(0)` 不会形成退出死循环

**它全程不接触用户真实的 `~/.claude/settings.json` 与 `~/.cc-nbproject/`。**

### 6.4 测试怎么写

- 用 `node --test`，**不引入 jest / vitest / puppeteer / playwright**。
- 涉及文件系统的一律 `mkdtemp` 造隔离目录，**不碰用户真实路径**。
- 临时目录**不做清理**（交给系统回收）—— 免得测试代码里出现任何 rm 类操作。
- 测试名写中文，说清「验的是什么行为」，不要写 `test1`、`should work`。
- **断言要断言行为，不要断言实现。** 尤其不要写「读被测对象自己算出的值，
  再断言界面等于它」这种同源自证的检查 —— 两边同源，算错了两边一起错，测试照样绿。
- 会破坏用户数据的回归**必须有测试钉死**。

### 6.5 错误处理约定

| 场景                                 | 约定                                                                           |
| ------------------------------------ | ------------------------------------------------------------------------------ |
| 用户可理解、可自行处理的失败         | **返回 `{ ok: false, reason }`，不抛**                                         |
| 调用方明确违约（参数缺失、状态非法） | **抛**，让 bug 尽早暴露                                                        |
| IPC 边界                             | 可以抛，`ipcRenderer.invoke` 会把异常转成渲染进程的 reject                     |
| HTTP 处理器内部                      | **绝不许让异常穿透监听器** —— 那会变成主进程未捕获异常，整个应用连代理一起消失 |

**任何 `ok: false` / `reason` 的文案都必须是给用户看的话**，不能是内部术语。
写「代理未运行，无法接管。请检查是否有端口被占用。」而不是 `EPROXYDOWN`。

### 6.6 CI

`.github/workflows/ci.yml` 把第 1、2 级变成合并前的硬门槛：

| job     | 平台      | 跑什么                                          |
| ------- | --------- | ----------------------------------------------- |
| `check` | ubuntu    | `npm run typecheck` → `lint` → `test` → `build` |
| `e2e`   | **macOS** | `npm run build` → `npm run e2e`                 |

两个刻意的安排：

- **e2e 必须是 macOS**：它验的是 `before-quit` 在真实退出路径上的行为，那是
  macOS 上的退出语义。换到 ubuntu 跑，验的就不是同一件事了。
- **e2e 只在 PR 上跑**：本仓库是私有仓库，而 GitHub Actions 的 macOS runner 按
  **10 倍**计入额度（免费额度 2000 分钟/月）。PR 是真正的合并门槛，
  放在那里收益最高、浪费最少。直接 push 到 main 的改动请在本地跑 `npm run e2e`。

**第 3 级（`smoke`）永远不进 CI** —— 它连的是**用户正在运行的实例**，
还要从用户已有的供应商里抄取真实 `baseUrl`/`apiKey`，CI 里两样都没有。

### 6.7 类型检查的覆盖范围（渐进式）

本仓库有**两份** tsconfig：

| 配置文件             | 覆盖                                         | 状态                                             |
| -------------------- | -------------------------------------------- | ------------------------------------------------ |
| `tsconfig.json`      | `src/renderer`                               | 完整（`strict: true`）                           |
| `tsconfig.main.json` | `src/main`、`src/preload`、`scripts`、`test` | **渐进式**：靠文件顶部的 `// @ts-check` 逐个纳入 |

`npm run typecheck` 会同时跑这两份。

**为什么主进程那份是渐进的**：`src/main/` 那六个模块约 6000 行 JS，
其中 `setup.js` 写错会改坏用户的 `~/.claude/settings.json`、`proxy.js` 写错会静默用错凭证 ——
而它们此前**只有 ESLint 的基础规则**（`no-undef`、`eqeqeq`）盯着，ESLint 根本不看类型。

但在 `checkJs: true` 下，这六个模块当前有 **210 个错误**（其中 178 个是「隐式 any」，
给参数补 JSDoc 类型注解即可）。一次性全开会**让 CI 从第一天起就是红的** ——
红着的门禁等于不存在。

所以采取渐进策略：

> **想推进哪个模块，就在该文件顶部加一行 `// @ts-check`，把该文件的错误清零。**

每一步都是绿的，覆盖范围只增不减。

| 模块             | 错误数 | 状态      |
| ---------------- | ------ | --------- |
| `usage.js`       | 1      | ✅ 已纳入 |
| `models.js`      | 14     | ⬜ 待推进 |
| `store.js`       | 21     | ⬜ 待推进 |
| `index.js`       | 22     | ⬜ 待推进 |
| `setup.js`       | 32     | ⬜ 待推进 |
| `proxy-agent.js` | 42     | ⬜ 待推进 |
| `proxy.js`       | 78     | ⬜ 待推进 |

> 建议的推进顺序是**按风险倒序**：先 `setup.js` 与 `proxy.js`（写错代价最大），
> 再 `proxy-agent.js`，最后收尾 `index.js`。

## 7. 故障排查

### 7.1 已知坑（踩过，别再踩）

1. **`ELECTRON_RUN_AS_NODE=1`**。这个环境变量会让 Electron 退化成普通 Node 进程，
   `app` 直接是 `undefined`，报错是
   `Cannot read properties of undefined (reading 'requestSingleInstanceLock')` ——
   看上去像主进程的 bug，其实是环境。
   跑任何 Electron 脚本用 `env -u ELECTRON_RUN_AS_NODE`。

   > ⚠️ **`npm run dev` 当前没有清掉它**，因此在设了这个变量的终端里
   > （比如本仓库的默认开发环境）会启动失败。这是已知缺陷，见第 8.5 节。

2. **`npm start` 之前必须 `npm run build`**。`dist/` 在 `.gitignore` 里，
   干净克隆直接 `npm start` 会白屏。

3. **单实例锁在模块顶层判定**。第二个实例会立刻退出，`--remote-debugging-port`
   根本不会打开。要用调试端口跑 `smoke.js`，得先退出正在运行的那个实例。

4. **端口会漂移**。8787 被占时代理会顺延到 8788…8807。任何需要写地址的地方都必须
   取 `proxy.baseUrl`，**不能写死 8787**。

5. **改渲染进程必须用真 Electron 验证**（见 6.2）。

6. **CDP 注入的页面代码，变量名会撞**。同一段页面代码里 `const card` 出现两次就是
   `SyntaxError`，而报错抛在页面里，从 Node 这边只看到一句含混的失败。

### 7.2 界面状态与含义

| 界面显示                        | 实际含义                             | 你该做什么                             |
| ------------------------------- | ------------------------------------ | -------------------------------------- |
| 已接管（`active`）              | 文件里那两个键确实等于我们写进去的值 | 不用管                                 |
| 已授权，本次未生效（`pending`） | 授权过，但这次没写进去               | 看界面给的原因：代理没起来？端口被占？ |
| 未接管（`off`）                 | 从未授权，或已断开                   | 想用就点「确认接管」                   |
| 「有 N 项被跳过」               | 你自己手改过那些键，我们没动         | 无需处理，这是保护行为                 |

### 7.3 出问题了怎么办

**Claude Code 突然连不上了**：

1. 应用是不是关着？**关着时代理不运行**，`ANTHROPIC_BASE_URL` 指向一个死端口。
   打开应用即可（会自动接管），或者点「断开接入」恢复原配置。
2. 打开应用仍不通 → 看供应商是否已激活、连接测试能否通过。

**想彻底恢复原状**：

- 点「断开接入」（会还原 + 清除授权记忆）
- 手工恢复：接管前的原值记录在 `~/.cc-nbproject/profiles.json` 的
  `settings.takeover.previous`；首次接管前的完整备份在
  `~/.claude/settings.json.bak.<时间戳>`（**只产生一次**）

**应用退不掉**：见 4.6 —— 若还原失败会弹框，点「仍然退出」即可。
若连框都没有，检查是否有 SSE 长连接挂着（`proxy.stop()` 有 2 秒上界，不该卡住）。

## 8. 决策记录与附录

### 8.1 关键取舍

| 决策                         | 为什么这么选                                              | 代价                                       |
| ---------------------------- | --------------------------------------------------------- | ------------------------------------------ |
| 代理跑在主进程               | 渲染进程是沙箱化浏览器环境，不能监听端口                  | 主进程代码量更大                           |
| 五个核心模块零 Electron 依赖 | `npm test` 不需要 GUI，几百毫秒跑完                       | 所有协作走参数注入，装配集中在 `index.js`  |
| 全部用工厂函数               | 最危险的代码（还原）必须能被 `mkdtemp` 测透               | 不能有模块级单例                           |
| 模型映射未命中返回 `null`    | 省一次序列化，且不破坏非 JSON 请求体                      | 调用方要处理 `null` 分支                   |
| 用量存 JSONL 而非 JSON 数组  | O(1) 追加                                                 | 读取要自己逐行解析，且要限制回看行数       |
| 不做自研加密                 | 主密钥同样得存本地，只是把问题挪一层                      | key 明文落盘，靠 `0600`                    |
| 引入 React                   | 界面状态（5 个 hook + 2 个模态框）用原生 DOM 已经难以维护 | 引入构建步骤（Vite）                       |
| 不引入 jest / puppeteer      | 零额外依赖，`node --test` + 全局 `fetch`/`WebSocket` 够用 | 工具链要自己写（`smoke.js`、`e2e/run.js`） |

### 8.2 事故档案（给「接管与还原」这个模块的评审）

2026-09-22 对本仓库做过一轮对抗性审查，**六条高危全部已修**，
每条都有单元测试或真 Electron 端到端钉死。完整判定原文与修复代码见
[审计发现与处置](./审计发现与处置.md)，这里只留**结论与教训**：

| 编号 | 缺陷                                                                 | 教训                                                 |
| ---- | -------------------------------------------------------------------- | ---------------------------------------------------- |
| H1   | `getActiveProfile()` 无 try/catch → 配置损坏带崩整个应用             | 每次请求都会调用的函数，**必须假设它会抛**           |
| H2   | `baseUrl` 兜底 `\|\| 'http://127.0.0.1:8787'` → 把死地址写进用户配置 | **宁可拒绝写入，也不要写一个猜的地址**               |
| H3   | `start()` 失败后状态不一致 → 再点重试静默返回 `null`                 | 失败路径必须把状态清干净，否则「重试」按钮点不动     |
| H4   | 接管单向、退出不还原、无还原入口                                     | **只接不管 = 用户关掉应用后 Claude Code 指向死端口** |
| H5   | 写回 `settings.json` 时权限被放宽到 `0644`                           | 原子写入的临时文件默认按 umask，**必须显式 `mode`**  |
| H6   | 同机任意进程可白嫖真实 key（凭证是公开常量）                         | 安全默认值不能用「大家都能猜到的东西」               |

**同轮修复的其它问题**：`stop()` 无上界导致退不掉、监听回退堆积死监听器、
预览显示一个用户找不到的备份文件名、没有单实例锁、文件损坏时还原会覆盖原配置。

**这些规矩用事故换来的代价**，值得贴在墙上：

| 规矩                    | 不遵守的代价                               |
| ----------------------- | ------------------------------------------ |
| 预览与应用严格分离      | 静默改坏配置后，用户无处可查               |
| 接管必须成对还原        | 关掉应用后 Claude Code 指向死端口          |
| 还原必须逐键三态判定    | 用户手动改的值被静默覆盖                   |
| 残渣不许记进 `previous` | 用户真实凭证被丢弃，工具还报「已还原成功」 |
| 写凭证不许用固定常量    | 同机任何进程都能借代理白用用户的真实 key   |
| 写地址不许写死端口      | 端口漂移时把连不上的地址写进用户配置       |

### 8.3 术语表

| 术语                           | 含义                                                                 |
| ------------------------------ | -------------------------------------------------------------------- |
| **接管（takeover）**           | 把 `~/.claude/settings.json` 的两个受管键改成指向本机代理            |
| **还原（restore）**            | 把两个受管键写回接管前的值（`previous`）                             |
| **受管键**                     | 只有 `ANTHROPIC_BASE_URL` 与 `ANTHROPIC_AUTH_TOKEN`，其余一概不碰    |
| **残渣（residual）**           | 上一次接管写进去、但没被正常还原的值                                 |
| **准入凭证（localToken）**     | 代理校验来客用的随机口令，写进 Claude Code 的 `ANTHROPIC_AUTH_TOKEN` |
| **`applied` / `previous`**     | 我们写进去的值 / 接管前用户的值                                      |
| **三态（off/active/pending）** | 接管状态的界面口径，判定以**文件内容**为准                           |
| **模型映射**                   | 把 Claude Code 发出的模型名改写成供应商认得的名字，未命中则原样转发  |
