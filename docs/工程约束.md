# 工程约束

> 给人读的完整规范：分层、约定、验证要求、评审清单。
> AI 执行时的硬规则在 [../CLAUDE.md](../CLAUDE.md) —— 那份是命令式的、去掉了理由；
> 这份保留理由，供人做判断与评审。
> 第一次接触这个仓库请先读[项目速览](./项目速览.md)。

---

## 1. 这个项目为什么需要「约束」这个文件

因为它会**改用户的真实文件**。

大多数项目写错代码的代价是「功能不工作」。这个项目写错 `setup.js` 的代价是
**用户的 Claude Code 突然不能用了，而用户完全想不到是本工具造成的** ——
这句话就写在 [setup.js](../src/main/setup.js) 的文件头里，是这个仓库的作者
自己写下的风险，并且在「接管与还原」那一轮工作之前**一直处于裸奔状态**
（只接管、不还原，关掉应用就断）。

所以这里的很多规矩不是风格偏好，是**用事故换来的**：

| 规矩                    | 换来的代价                                 |
| ----------------------- | ------------------------------------------ |
| 预览与应用严格分离      | 静默改坏配置后，用户无处可查               |
| 接管必须成对还原        | 关掉应用后 Claude Code 指向死端口          |
| 还原必须逐键三态判定    | 用户手动改的值被静默覆盖                   |
| 残渣不许记进 `previous` | 用户真实凭证被丢弃，工具还报「已还原成功」 |
| 写凭证不许用固定常量    | 同机任何进程都能借代理白用用户的真实 key   |
| 写地址不许写死端口      | 端口漂移时把连不上的地址写进用户配置       |

## 2. 分层与依赖方向

```
renderer (React, 无 fs/net)
    │  window.ccnb.*  ← preload 白名单
    ▼
preload (contextBridge)
    │  ipcRenderer.invoke('域:动作')
    ▼
main/index.js  ← 装配 + IPC 编排 + 生命周期
    ├── proxy.js        纯 Node，零 Electron 依赖
    ├── proxy-agent.js  纯 Node
    ├── setup.js        纯 Node（只 fs）
    ├── store.js        纯 Node（只 fs）
    ├── models.js       纯 Node
    └── usage.js        纯 Node（只 fs）
```

**硬规则：**

1. **依赖只能向下。** `proxy.js` 不许 `require('electron')`，
   `setup.js` 不许 `require('./store')`。所有跨模块协作走参数注入。
   这条不是洁癖 —— 它是 `npm test` 能在几百毫秒内跑完**上百个**用例、
   且完全不需要 GUI 的唯一原因。
2. **`index.js` 是唯一的装配点。** 想在别处 `new` 一个模块级单例，先问为什么。
3. **渲染进程永远不碰系统。** 需要新能力 = 新增 IPC + preload 登记 + `types.ts` 补类型。

### 为什么坚持工厂函数而不是模块级单例

`createStore({ dir })` / `createSetup({ claudeDir, localToken })` / `createProxy({...})` /
`createUsageStore({ dir })` / `createModelFetcher({...})` —— 全部可以注入路径或依赖。

因为**必须能被测试的恰好是最危险的那段代码**：还原逻辑写错就毁掉用户的
Claude Code 配置，而它偏偏是「路径写死在模块顶层时最测不了」的部分 ——
想测一次就得去读写用户的私人文件。注入之后，测试可以用 `mkdtemp` 把它测透。

## 3. 注释的写法

这个仓库的注释密度高于一般项目，且**只写「为什么」，几乎不写「什么」**。

判断一段注释该不该存在，看它回答的是哪个问题：

- ❌ `// 遍历 profiles` —— 代码自己说了，删掉
- ✅ `// 第一个添加的供应商自动激活，省去用户一次多余点击` —— 说清了取舍
- ✅ `// 用 hasOwnProperty 而不是 \`|| null\`：""、0、false 都是合法取值，
  // 被折叠成 null 会让还原把「空串」和「键不存在」混为一谈` —— 记下了踩过的坑

**特别要写的三类：**

1. **反直觉的实现选择**。凡是「看上去可以更简单、但这里故意没这么做」的地方，
   必须写清另一条路的代价。例：`stop()` 为什么要清引用再 close。
2. **事故记忆**。修过一个造成数据破坏的 bug，就把那次的现场写进注释。
   例：`makeBackupPath()` 上「预览显示的名字和真正生成的对不上」那段。
3. **平台/运行时的怪癖**。例：`window-all-closed` 在应用退出时不触发。

**不要写的**：段落级的「本函数用于…」、逐行翻译、TODO 堆。

文件头的注释应当回答：**这个文件是干什么的、为什么这么设计、改它要小心什么。**

## 4. 错误处理约定

| 场景                                 | 约定                                                                           |
| ------------------------------------ | ------------------------------------------------------------------------------ |
| 用户可理解、可自行处理的失败         | **返回 `{ ok: false, reason }`，不抛**                                         |
| 调用方明确违约（参数缺失、状态非法） | **抛**，让 bug 尽早暴露                                                        |
| IPC 边界                             | 可以抛，`ipcRenderer.invoke` 会把异常转成渲染进程的 reject                     |
| HTTP 处理器内部                      | **绝不许让异常穿透监听器** —— 那会变成主进程未捕获异常，整个应用连代理一起消失 |

第二类与第一类的分界举例：

- `applyClaudeSettings({ proxyBaseUrl: '' })` → **抛**。这是调用方违约，
  说明 R7 的准入检查漏了，应当炸在开发期而不是写进用户配置。
- `previewClaudeSettings()` 在代理未就绪时 → **返回 `{ ok: false, reason }`**。
  用户看到「代理未运行，无法接管」并知道该去查端口占用，比一句异常有用。

**任何 `ok: false` / `reason` 的文案都必须是给用户看的话**，不能是内部术语。
「代理未运行，无法接管。请检查是否有端口被占用。」而不是 `EPROXYDOWN`。

## 5. 验证策略（三级，不可跳级）

### 第 1 级 —— 静态与单元（每次改动都要跑）

```bash
npx tsc --noEmit && npm run lint && npm test
```

覆盖：纯逻辑、文件读写（`mkdtemp` 隔离目录）、代理转发（本地假上游）。
**不覆盖**：渲染进程能否渲染、Electron 生命周期。

### 第 2 级 —— 真 Electron 端到端（改动 `index.js` 生命周期或渲染进程时必跑）

```bash
npm run e2e
```

`scripts/e2e/run.js`：在 `mkdtemp` 造出的隔离 HOME 上启动**生产入口**，
用 CDP 驱动界面完成「接管 → 校验文件 → 用真实退出路径关掉 → 校验文件已还原」，
覆盖 5 个场景（含「断开后不再接管」与「接入前文件不存在」）。

它专门验两件静态检查永远验不了的事：

1. 渲染进程真的渲染出来了（不是白屏）
2. `before-quit` 真的会触发、`app.exit(0)` 不会形成退出死循环

### 第 3 级 —— 真实窗口冒烟（改动界面交互时跑）

```bash
# 另一个终端
env -u ELECTRON_RUN_AS_NODE npx electron . --remote-debugging-port=9222
# 本终端
npm run smoke
```

`scripts/smoke.js` 连**用户正在用的那个实例**去点，因此有一条铁律：

> **它绝不改动用户已有的任何数据。** 所有写操作只落在一个当场新建的一次性
> 供应商 `__smoke__` 上，结束时无条件删除，并逐字段比对你原有的配置一字未改。

这条是踩坑换来的：早先的版本直接在真实 profile 上改、收尾再还原，
结果脚本运行期间用户自己点了一下界面 —— 「还原」把他刚选的值覆盖了。
**检查工具不该留下任何能改动用户数据的窗口期。**

## 6. 改动检查清单

按你动的那一层逐条过一遍。

### 动了 `src/renderer/**`

- [ ] `types.ts` 里补了新的数据结构
- [ ] `npx tsc --noEmit` 干净
- [ ] **真 Electron 里点过一遍**（不是只看构建成功）
- [ ] 新增的 `data-*` 属性没有随意改名（冒烟脚本靠它选元素）

### 动了 IPC（新增/改名通道）

三处必须同时改，缺一不可：

- [ ] `src/main/index.js` 的 `ipcMain.handle`
- [ ] `src/preload/index.js` 的白名单方法
- [ ] `src/renderer/types.ts` + `src/renderer/ccnb.ts` 的类型

### 动了 `src/main/setup.js`

- [ ] 仍然只碰 `MANAGED_KEYS` 里的两个键
- [ ] 新的写入路径想清楚了它的还原路径
- [ ] 预览路径**没有**写入任何东西
- [ ] `previous` 的刷新规则没有被破坏（先跑 `test/setup.test.js` 第 10、11 条）
- [ ] 仍然保持 `createSetup({ claudeDir })` 形态

### 动了 `src/main/index.js` 的生命周期

- [ ] 还原仍然只在 `before-quit` 里做一次
- [ ] 没有引入 `SIGINT` / `SIGTERM` 处理器
- [ ] `app.exit(0)` 而不是 `app.quit()`（后者会重新触发 `before-quit` → 死循环）
- [ ] 单实例锁仍在模块顶层，落败分支仍不做还原
- [ ] `npm run e2e` 五个场景全绿

### 动了 `src/main/proxy.js`

- [ ] 仍然零 Electron 依赖
- [ ] 准入校验仍在最前面（未带凭证的请求**一次上游都不该打到**）
- [ ] 发往上游的仍是 `profile.apiKey`，不是客户端的凭证
- [ ] `start()` 失败时清空了 `server`
- [ ] `stop()` 仍然有超时上界

## 7. 测试与检查脚本的约定

- **零额外依赖。** `node --test` + 全局 `fetch` / `WebSocket`。
  引入 jest / vitest / puppeteer / playwright 需要先说服维护者。
- **隔离。** 涉及文件系统一律 `mkdtemp`。临时目录**不清理**（交给系统回收）——
  免得测试代码里出现任何 rm 类操作。
- **不自证。** 断言不许拿被测对象自己算出的值去断言它自己。
  反例：读 `status.fileMatches` 再断言界面显示「已接管」——
  两边同源，`fileMatches` 算错了两边一起错，测试照样绿。
  正例：脚本自己读 `settings.json`，自己算出应该是什么状态，再和界面对。
- **不静默截断。** 检查里若有「跳过」「只测前 N 个」的分支，
  必须把跳过的那条也打印出来。静默跳过读起来等于「全都验过了」。
- **输出会被人整段复制。** 报错信息里不许出现 API key 或凭证，
  用长度 + 前几位代替（见 `scripts/smoke.js` 的 `redact` / `redactEnv`）。

## 8. 文档约定

| 目录          | 放什么                                | 命名                     |
| ------------- | ------------------------------------- | ------------------------ |
| `docs/`       | 常青文档：速览、架构、约束、审计      | 中文名，如 `架构说明.md` |
| `docs/plans/` | 带日期的过程产物：设计、实现计划、PRD | `YYYY-MM-DD-主题.md`     |
| `CLAUDE.md`   | AI 硬规则                             | 固定名                   |
| `README.md`   | 面向使用者：是什么、怎么装、怎么用    | 固定名                   |

**写 PRD 时的规矩**（见 `docs/plans/` 里已有的三份）：

- 开头必须有 `> 状态：` 一行，取值 `待批准` / `已批准` / `已实施`，
  外加一行实测结论的链接。**读者必须能一眼分辨「已实现」与「只是计划」。**
- 需求条目编号 `R1`、`R2`…，每条都能被单测或 E2E 对应上。
- 推翻前一版时不要删掉旧版，写成文末的「附」，说清为什么推翻。

**站内链接一律用相对路径**，并指向真实的文件或行号。
移动文档时，**必须同时搜一遍全仓库有没有别的文件链到它**。
