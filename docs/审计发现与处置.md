## H1 —— 配置文件损坏会带崩整个应用

### 判定原文

> `proxy.js:251` getActiveProfile() 无 try/catch → 带崩主进程

### 为什么是高危

`getActiveProfile()` 每次请求都会调用，它读的是 `profiles.json`。
用户在应用运行期间手工编辑那 个文件、把 JSON 写坏（或磁盘写了一版半截文件）之后：

- 抛出的异常**穿透 `http.createServer` 的请求监听器**
- 变成主进程的未捕获异常 → 整个应用退出，代理一起消失
- 而对面的 Claude Code 只看到**连接被重置**，拿不到任何可解释的响应
- 用户此时面对的是一个「刚崩掉的 GUI + 一个不能用但没有任何提示的 Claude Code」

### 处置

`handleRequest` 里包住：

```js
let profile;
try {
  profile = getActiveProfile();
} catch (err) {
  onRequest({ phase: 'error', error: err.message, profileName: null });
  sendJson(clientRes, 500, {
    type: 'error',
    error: { type: 'config_unreadable', message: `读取供应商配置失败：${err.message}` },
  });
  return;
}
```

要点是**转成一条可读的 500**：应用活着、界面能把提示显示出来、用户知道该去修哪个文件。

## H2 —— 把死地址写进用户的配置

### 判定原文

> `index.js:148/152` baseUrl 兜底 → 死地址写入用户配置

### 为什么是高危

原代码是 `proxy.baseUrl || 'http://127.0.0.1:8787'`。这个 `||` 的兜底在
**代理根本没起来**（端口全被占、绑定失败）时，会把一个必然连不上的地址
写进 `~/.claude/settings.json`。

这正是本工具最该避免的那类故障：**用户完全想不到是工具造成的**。
Claude Code 从此连不上，而用户手上没有任何线索指向这里。

它还有第二个问题：端口被占时代理会顺延（8787 → 8807），写死的 `8787`
**跟实听端口不是一回事**。

### 处置

两道防线：

1. `applyClaudeSettings({ proxyBaseUrl })` 在 `proxyBaseUrl` 为空时**直接抛错**，
   拒绝写入。地址一律取自 `proxy.baseUrl`（实听端口）。
2. `index.js` 的准入检查 `checkTakeoverEligibility()`：代理不在监听、或没有已激活的
   供应商，一律**不出预览、不执行接管**，只回一条可读的原因。

## H3 —— 启动失败后再也起不来

### 判定原文

> `proxy.js:486-491` start() 失败后状态不一致，再 start() 静默返回 null

### 为什么是高危

`start()` 第一行是 `if (server) return actualPort;`。失败路径上没有把 `server`
清回去，于是**第二次** `start()` 命中这一行，返回 `null` —— 不抛错、不重试、
不监听。

界面上表现为：代理起不来，用户点「重试」毫无反应。

### 处置

```js
const candidate = http.createServer(handleRequest);
server = candidate;
try {
  actualPort = await listenWithFallback(candidate, port, host);
} catch (err) {
  server = null;
  actualPort = null;
  try { candidate.close(); } catch {}
  throw err;
}
```

半开的实例也要关掉，否则它持有的 handle 会拖住进程退出。

## H4 —— 接管是单向的，而且没有回头路

### 判定原文

> 接管单向，退出不还原，无还原入口

### 为什么是高危

`ANTHROPIC_BASE_URL` 被改成 `http://127.0.0.1:8787`（本机代理），而应用一关代理就停了。
退出路径上只有 `proxy.stop()`，**从不还原配置文件**。

结果：用户点了「一键接入」，然后关掉应用 —— Claude Code 随即指向一个没人监听的端口。
而当时**没有任何还原入口**（IPC 只有 `claude:preview` 和 `claude:apply`，没有 revert），
用户唯一的退路是手工编辑 `~/.claude/settings.json`，或去比对那个
`settings.json.bak.<时间戳>`。

这一条尤其刺眼，因为 [setup.js](../src/main/setup.js) 的文件头自己写着：
「一旦改坏，用户会看到 Claude Code 突然无法使用，却完全想不到是这个工具造成的，
排查成本极高」—— 作者写下了这条风险，而它当时正是裸奔状态。

### 处置

按 PRD 实现「一次授权、长期记住；开应用才生效，关应用自动还原」。

**其中最容易做错、也最容易看起来做对的一处是退出钩子。** 原先的想法是把还原挂在
`window-all-closed` 上 —— 但**那个事件在「应用正在退出」时根本不触发**，
而 macOS 上最常见的退出路径 Cmd+Q 正是「应用正在退出」。也就是说，
挂在 `window-all-closed` 上的还原，在最主要的路径上从不执行，
而开发者在本机点关闭按钮测试时**它会正常工作**。

所以还原收口到单一出口：

```js
app.on('before-quit', async (event) => {
  if (quitHandled) return;
  event.preventDefault();
  // …还原（含失败时告知用户）…
  await proxy.stop();
  quitHandled = true;
  app.exit(0);   // 用 exit 而不是 quit：quit 会重新触发 before-quit → 死循环
});
```

不注册 `SIGINT` / `SIGTERM`：macOS 上从 Finder/Dock 启动的 .app 没有控制终端，
收不到 Ctrl+C；系统注销走的也是 quit Apple Event（即 `before-quit`）。
那两个处理器对真实用户路径覆盖为零，却会和 Electron 自己的退出流程打架。

**这个修复由 `npm run e2e` 专门验证**：它用一个独立的退出信号文件让应用调用
`app.quit()`（与 Cmd+Q 同一条路径），然后断言文件已还原。
从页面上关窗口走的是另一条路径 —— 恰好验不到这条。

## H5 —— 写回配置时把权限放宽了

### 判定原文

> `setup.js:138` 权限放宽到 0644

### 为什么是高危

原子写入是「写临时文件 → `rename` 覆盖」。`fs.writeFileSync` 不传 `mode` 时，
临时文件按 `0o666 & ~umask` 创建 —— 通常是 `0644`。`rename` 之后，
**用户原本 `0600` 的 `settings.json` 就被静默放宽了**。

那个文件里存着用户的真实 API key。同机其他用户从此可以直接读到它。

这个缺陷的恶劣之处在于：功能完全正常，没有任何征兆，而下一次「备份」还会
把放宽后的版本一起备份走。

### 处置

```js
fs.writeFileSync(tmpPath, content, { mode: FILE_MODE });   // 显式 0600
fs.renameSync(tmpPath, settingsPath);
fs.chmodSync(settingsPath, FILE_MODE);                      // rename 后再收紧一次
```

`test/setup.test.js` 第 1 条直接断言 `fs.statSync(settingsPath).mode & 0o777 === 0o600`。

## H6 —— 同机任何进程都能白嫖用户的真实 key

### 判定原文

> 本地任意进程可白嫖真实 key

### 为什么是高危

代理监听 `127.0.0.1`，本意是「只有本机能访问」。但**「本机」不等于「本用户」**：
同一台机器上的任何进程、任何账户，只要能连 `127.0.0.1:8787`，就能让代理拿
**用户真实的 API key** 去发请求并计费。

而代理的转发逻辑刻意丢弃客户端凭证、无条件换成 `profile.apiKey` ——
这本来是为了支持「零重启切换」（Claude Code 不必知道真实 key），
但它同时把代理变成了一个**敞开的中转站**。

更糟的是当时写进 Claude Code 的 `ANTHROPIC_AUTH_TOKEN` 是一个**公开常量**
`cc-nbproject-managed`。也就是说那串字本身就是「请随便用」的通行证，
写在源码里，任何进程照抄即可。

### 处置（这条不在 PRD 范围内，是另外设计的）

把「本地准入凭证」从公开常量改成**每次安装随机生成**：

| 环节 | 位置 | 行为 |
|---|---|---|
| 生成 | `store.getLocalToken()` | 32 字节随机数的十六进制（64 位），首次调用时生成并落盘 |
| 写入 | `setup.buildNextSettings()` | 接管时写进 `ANTHROPIC_AUTH_TOKEN` |
| 校验 | `proxy.holdsLocalToken()` | 代理只认它：`Authorization: Bearer <token>` 或 `x-api-key: <token>` |

凭证与 API key 同存于 `profiles.json`（权限 `0600`），**不增加新的暴露面** ——
能读到这个文件的人本来就已经拿到了所有真实 key。

老安装兼容：旧版本写进配置的是公开占位符。它**不会**被继续接受（接受就等于
把洞留着），但会被 `looksLikeOurOwnValue` 认作「我们自己留下的残渣」，
于是在下一次接管时被正确覆盖，且**不会被误记进 `previous`**。

## 同轮一并修复的其它问题

按后果排列，均为实现 H2/H3/H4 的过程中顺带处理的。

### 1. `proxy.stop()` 没有上界 —— 关掉窗口后应用再也退不掉

`server.close()` 要等**所有已建立的连接结束**才回调。而代理给 Claude Code 服务的
那条转发路径（SSE 长连接）没有任何超时，用户正开着会话时这个等待**没有上界** ——
而退出流程会 `await` 它。

修法：给 `close` 加一个有界等待（默认 2 秒），超时后主动 `closeAllConnections()`。
并把 `server` / `actualPort` 的清理提到 `close()` 之前 —— `close()` 可能永远不回调，
留着引用的话之后的 `start()` 会被挡住。

守护：`test/proxy.test.js`「停止代理：有连接挂着时也在超时内返回」。

### 2. 监听回退会堆积死监听器

`listenWithFallback` 只用 `server.once('error', ...)`，而在端口被占时
`listen(port, host, cb)` 注册的那个一次性 `listening` 监听器**永不触发也永不被移除**。
连续回退 20 次就在同一个 server 上堆 20 个死监听器，Node 以
`MaxListenersExceededWarning` 警告潜在的内存泄漏。

修法：`cleanup()` 同时摘掉 `error` 与 `listening` 两个监听器，
改用 `server.once('listening', onListening)` 而不依赖 `listen` 的回调参数。

### 3. 预览显示一个用户找不到的备份文件名

`previewClaudeSettings` 与 `applyClaudeSettings` 各自调了一次 `makeBackupPath()`，
而那个名字里带时间戳 —— **两次调用必然得到不同的名字**。界面上写着
「写入前会自动备份为：…bak.10-00-00」，用户写完去找，那个文件不存在。

修法：预览只返回布尔语义 `willBackup`，具体路径由接管结果给出。

守护：`test/setup.test.js` 第 13b 条断言预览结果里**没有** `backupPath` 字段。

### 4. 没有单实例锁

两个实例会同时持有接管状态：先退出的那个执行还原，把仍在运行的另一个实例的接管
撤掉，用户表现为「用着用着突然断了」。

修法：`app.requestSingleInstanceLock()` 放在**模块顶层**（早于任何退出钩子注册、
也早于 `proxy.start()` 与启动接管），落败分支**不做任何还原** ——
它读到的接管状态是另一个实例写的，它无权撤销。

顺带：`bootstrap()` 把全部副作用包起来。放在模块顶层的话，失败分支一旦执行到那里，
会在用户毫不知情的情况下生成 `~/.cc-nbproject/profiles.json` 并写入本地准入凭证 ——
一个「什么都不做」的退出不该有这种副作用。

### 5. `settings.json` 被改坏时，还原会把它覆盖掉

用户的 `settings.json` 本身不是合法 JSON 时，原先的行为是继续走写入流程 ——
那会把用户原有的配置彻底抹掉。

修法：`readCurrentSettings()` 在解析失败时抛错，调用方不写入任何内容。
守护：`test/setup.test.js` 第 7 条断言「抛错且一个字节都不写」。

## 这些修复靠什么守住

| 层次 | 工具 | 数量 |
|---|---|---|
| 单元测试 | `npm test` | 123 个用例，其中接管/还原 18 个、代理准入与生命周期 8 个、store 9 个 |
| 类型与规范 | `npx tsc --noEmit` / `npm run lint` | 全绿 |
| 真 Electron 端到端 | `npm run e2e` | 5 个场景，含「退出后文件已还原」 |
| 真实窗口冒烟 | `npm run smoke` | 含「侧边栏接管状态行与 settings.json 内容是否一致」（只读） |

**注意最后两条的必要性**：H4 的修复（退出钩子迁移）**根本不可能被单元测试发现** ——
它错在「事件在真实退出路径上不触发」，而单测里根本没有 Electron 的事件循环。
这就是本仓库坚持「改生命周期必须跑 `npm run e2e`」的原因。
